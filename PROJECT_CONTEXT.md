# MERA — Project Context for AI Assistants

Paste this whole document into a new conversation with Claude, ChatGPT, or any AI assistant before asking for help on this project. It gives the assistant the context it needs to give suggestions that actually fit our architecture instead of generic advice.

## What MERA is

MERA (Medical Emergency Response Application) is a South African medical emergency platform connecting **patients**, **hospitals**, and **ambulance services**. It's a year-long capstone project for a team called NonaCrest, with formal SRS and UI specification documents behind it. It must comply with South Africa's POPI Act (data protection law).

## Repo structure

Single repo, three top-level folders:

```
MERA-APP-Nonacrest/
├── backend/           Django REST Framework API (single backend, shared by both frontends)
├── mobile-frontend/   React Native / Expo app — for Patients and EMTs
└── web-frontend/      React + Vite app — for Hospital Admins, Ambulance Admins, and MERA super-admins
```

**One backend serves both frontends.** Nothing is duplicated. Any new endpoint should be built once in `backend/` and consumed by whichever frontend(s) need it.

## User roles (this is the most important part to get right)

There are **five roles**, and each has a specific home:

| Role | Where they log in | What they do |
|---|---|---|
| **Patient** | Mobile app | Self-registers. Triggers SOS, manages own medical profile, uses AI chatbot. |
| **EMT** | Mobile app | Does **not** self-register. Their account is created by their Ambulance Admin. Responds to SOS alerts, updates incident status, submits treatment notes. |
| **Hospital Admin** | Web app | Does **not** self-register. Account created by MERA super-admin during institutional onboarding. Manages patient verification queue, sees incoming ambulance notifications. |
| **Ambulance Admin** | Web app | Does **not** self-register. Account created by MERA super-admin. Creates/manages EMT accounts under their service. |
| **MERA super-admin** | Web app | Internal MERA team only. Onboards new hospital/ambulance institutions, creates their admin accounts, manages/deletes any account platform-wide, views platform stats. |

**Key principle: only Patients self-register.** Every other role's account is created by someone above them in the hierarchy (MERA admin → Hospital/Ambulance admin → EMT). This replaced an earlier design where hospitals and ambulances self-registered with a multi-step approval flow — that flow is being phased out in favor of top-down account creation.

**Important, still evolving:** Hospitals and hospital-related screens are being **removed from the mobile app entirely** and moved fully to the web app. The mobile app will end up serving only Patients and EMTs.

**Role naming — current transitional state (read this carefully before touching `accounts/models.py`):**

The `Role` enum on `User` currently has **seven** values, not five, because the new roles were added *alongside* the old ones rather than replacing them yet:

```
patient            — unchanged, still used
hospital           — OLD name for what is becoming hospital_admin. Still referenced
                      throughout permissions.py, views.py, verification app, etc.
ambulance_service  — OLD name for what is becoming ambulance_admin. Same situation.
hospital_admin     — NEW. Not yet wired into permissions/views beyond the model choice
                      and the web login page's role check.
ambulance_admin     — NEW. Same as above. This is an institution-level account
                      (the ambulance service itself), NOT an individual EMT.
emt                — NEW. Individual crew member, mobile-only, does not self-register.
                      Belongs to exactly one ambulance_admin (see field below).
mera_admin          — NEW. Platform-wide super-admin, web-only.
```

**This is a deliberate, temporary state.** The team has not yet decided whether to do a hard rename (`hospital` → `hospital_admin`, `ambulance_service` → `ambulance_admin`) across every file that references the old names, or to migrate references gradually. **Update:** old and new role names are now treated as equivalent everywhere permission/role checks happen. `accounts/models.py` defines `HOSPITAL_ROLES = {Role.HOSPITAL, Role.HOSPITAL_ADMIN}` and `AMBULANCE_ROLES = {Role.AMBULANCE_SERVICE, Role.AMBULANCE_ADMIN}`, and `IsHospital`, `IsAmbulanceService`, `HospitalListView`, and other role filters across `accounts/`, `verification/`, and `emergencies/` all check membership in these sets (`role__in=HOSPITAL_ROLES`, etc.) rather than a single literal role string. Accounts created with either the old or new role name are treated identically by these checks. The underlying rename decision (collapsing to one canonical name per role) is still not made — these sets are the interim bridge — but the practical blocker (new-role accounts failing old-name-only checks) described in earlier versions of this doc has been resolved.

**EMT ↔ Ambulance Admin link:** Each EMT belongs to exactly one ambulance service. This is modeled as a self-referencing `ForeignKey` on `User`:

```python
ambulance_service = models.ForeignKey(
    "self", null=True, blank=True, on_delete=models.SET_NULL,
    related_name="emts", limit_choices_to={"role": "ambulance_admin"},
)
```

An `ambulance_admin` user's EMTs are accessible via `ambulance_admin_user.emts.all()`.

**Account creation hierarchy (planned, not yet built):**
- MERA admin creates hospital_admin accounts and ambulance_admin accounts (institution onboarding)
- Ambulance admin creates EMT accounts (EMTs never self-register)
- Nobody creates MERA admin accounts through the app — these are set up directly (e.g. via Django shell) since it's the internal MERA team only

**Web login page:** Built at `web-frontend/src/pages/auth/Login.jsx`. Users select their role (MERA Admin / Hospital Admin / Ambulance Admin) via tabs *before* entering credentials. The frontend compares the selected role against `response.user.role` from the login API and **rejects login client-side if they don't match**, even though the backend would otherwise authenticate successfully. This is a deliberate UX choice, not a security boundary — real authorization still happens via backend permission classes on each endpoint.

## Tech stack

- **Backend:** Django REST Framework, PostgreSQL, JWT auth (`djangorestframework-simplejwt`)
- **Mobile frontend:** React Native + Expo (TypeScript)
- **Web frontend:** React + Vite (JavaScript), `react-router-dom` for routing, `recharts` for charts, `lucide-react` for icons. Folder structure under `src/pages/` is split by role (`auth/`, `hospital-admin/`, `ambulance-admin/`, `mera-admin/`) so each teammate can work in their own lane. Only `auth/Login.jsx` exists so far — the other three folders are still empty placeholders (`.gitkeep` only).
- **AI chatbot:** Server-side only, calls the Anthropic API from Django (never from either frontend — API keys must never touch client code)
- **Hosting:** Backend deployed on Render (free tier — **512MB RAM**, gunicorn pinned to `--workers 2 --timeout 30` in `Procfile`; see "Deployed backend OOM-killed..." under the `accounts` app section for the full investigation — the real cause was Render blocking outbound SMTP ports, not worker count or memory exhaustion, which is why email delivery for the OTP feature goes through Brevo's HTTP API rather than Gmail SMTP). Database also on Render Postgres (free tier — **expires and must be recreated roughly every 30 days**, so don't assume data persists indefinitely on the dev database). File storage (required institution-onboarding documents — see the `accounts` app section) is Cloudinary, not Render's own disk — same reasoning as the database/email choices above: Render's filesystem is ephemeral, so local `MEDIA_ROOT` storage would lose every uploaded document on the next deploy. Web frontend deployed separately (Vite static build); its own URL is configured backend-side via `WEB_FRONTEND_URL` (see "Password reset" under the `accounts` app section) so password-reset emails link to the right place per environment — must be kept in sync with wherever the web app actually gets deployed.

## Backend app structure (Django apps)

- `accounts` — custom `User` model with a `role` field. Currently holds both old (`hospital`, `ambulance_service`) and new (`hospital_admin`, `ambulance_admin`, `emt`, `mera_admin`) role values simultaneously — see the "Role naming" section above before changing anything here. Endpoint additions:
  - Ambulance admin — EMT management: `PATCH /auth/admin/emts/{id}/` (edit `full_name`/`phone_number`/`email` on your own EMT — role and password are not editable here) and `DELETE /auth/admin/emts/{id}/` (soft-deactivate: sets `is_active=False`, does **not** hard-delete — same pattern as institutional approval/rejection, chosen because it's the only removal pattern already in this codebase and it preserves incident/treatment-note history). Both `IsAmbulanceService`-gated and scoped to EMTs where `ambulance_service == request.user`; an EMT belonging to a different ambulance service returns 404 (not 403) so ownership isn't leaked, matching `verification`/`medical_profiles`'s existing lookup pattern.
  - MERA admin — institutions/stats/accounts (`IsMERAAdmin`-gated): `GET /auth/admin/institutions/` (hospital_admin + ambulance_admin accounts, both old/new role names via `HOSPITAL_ROLES`/`AMBULANCE_ROLES`; `InstitutionSummarySerializer` now also returns `is_active` — it didn't before, only `institutional_status`, a different field, which meant the frontend had no way to tell a deactivated institution from an active one) and `GET /auth/admin/users/` (every account, any role) both accept `?search=` — case-insensitive partial match, OR'd across whichever name field the row actually has populated (`full_name`/`facility_name`/`service_name`) plus `email`; safe to apply the same combined filter regardless of role since an irrelevant field is just blank and never matches. `GET /auth/admin/users/` also now orders `-is_active` first (active accounts before deactivated ones), then `-date_joined` as the tiebreaker within each group — it used to be pure `-date_joined`. `GET /auth/admin/stats/` (counts: patients, hospitals, ambulance services, EMTs, `emergencies.Incident` total) — the four role-based counts now filter `is_active=True`; previously they counted every account ever created regardless of status, so e.g. deactivating an ambulance_admin's EMTs never moved the dashboard number at all. `total_incidents` is unaffected — an `Incident` has no active/inactive concept. Covered by `accounts/tests.py::MERAAdminInstitutionsStatsUsersTest::test_stats_only_counts_active_accounts` (the pre-existing `test_stats` alone couldn't prove this, since its fixtures are all active by default — it would've passed identically with or without the filter). `PATCH /auth/admin/users/{id}/` — new: MERA admin edits any account's basic info (`full_name`/`email`/`phone_number`/`facility_name`/`service_name`); role and password are deliberately not editable here (role is permanent, password changes go through the reset flow) — see `AdminUserEditSerializer`. `PATCH /auth/admin/users/{id}/deactivate/` (sets `is_active=False` on any account regardless of role; a MERA admin can still deactivate another mera_admin's account, but is blocked with 400 from deactivating their *own* account, to prevent accidental self-lockout) **now cascades**: deactivating an ambulance_admin (or legacy ambulance_service) also deactivates every currently-active EMT linked to it via `.emts` — an EMT under a shut-down service shouldn't be able to keep responding to incidents. Hospital admins have no subordinate accounts, so nothing cascades for them. Response now includes `deactivated_emt_count`. `PATCH /auth/admin/users/{id}/reactivate/` — new: `ReactivateUserView`, the inverse. No role restriction (mirrors deactivate) and deliberately no self-lockout-style guard — `djangorestframework-simplejwt`'s `JWTAuthentication.get_user()` already re-checks `is_active` against the DB on *every* authenticated request, not just at login, so a deactivated account's own token already stops working before its next request goes through; a MERA admin cannot be authenticated while their own account is inactive, so "reactivate yourself" can't arise through the API at all. Also cascades the same way deactivate does — reactivating an ambulance_admin reactivates every currently-inactive EMT linked to it too (`reactivated_emt_count` in the response), otherwise cascading deactivation would be a one-way trip requiring the admin to manually reactivate each EMT individually afterward. No "already active" guard either, matching deactivate's own lack of an "already inactive" guard — both directions are idempotent successes, not errors.

**Institution reassignment (`successor_of`) — new.** `HospitalAdminCreationSerializer`/`AmbulanceAdminCreationSerializer` (i.e. `POST /auth/admin/create/hospital-admin/` and `.../create/ambulance-admin/`) now accept an optional `successor_of` field: the id of an existing **deactivated** account of the *same* institution type. Used when a hospital/ambulance's admin account was deactivated (e.g. staff turnover) and MERA is onboarding a replacement admin for the same physical institution, rather than starting from a blank slate. Validation (`_validate_successor` in `accounts/serializers.py`) rejects — with a clear `successor_of` field error, not a generic 400 — a target that doesn't exist, isn't deactivated, or is the wrong role type (e.g. pointing an ambulance creation at a deactivated hospital). When valid: `HOSPITAL_IDENTITY_FIELDS`/`AMBULANCE_IDENTITY_FIELDS` (facility/service identity — name, type, address, dispatch info, etc.) are copied from the old account onto the new one, **overriding** whatever those specific fields were set to in the request body — continuity of the institution's identity is the point, so the old account wins. The new admin's own `email`/`password`/`admin_contact_name`/`admin_phone` are never touched by this — those are the incoming person's, not inherited. For ambulance reassignment specifically, every EMT still pointing at the old account's `ambulance_service` FK is re-linked to the new account **and reactivated** in the same `.update()` call (regardless of their prior `is_active` state) — that's the actual intent of reassignment ("this new admin can use these EMTs again"), not a two-step process where re-linking happens now and someone has to remember to reactivate each EMT separately later. (`ReactivateUserView`, documented above, is the standalone version of this same reasoning — independently useful for reactivating a single account without a full reassignment.) The old account itself is left exactly as-is: still deactivated, still in the database, still the correct attribution on every historical `Incident`/`VerificationRequest` that already pointed at it — nothing about this flow touches those records, only the *current* EMT-linkage and institution-identity fields on the User rows change. Hospitals have no subordinate accounts, so hospital reassignment is just the identity-field copy, no re-linking step. Covered by `accounts/tests.py::InstitutionReassignmentTest`.

**Shared row-actions menu (web frontend) — new.** `web-frontend/src/components/UserRowActions.jsx` is a single component (a "⋮" menu — Edit / Deactivate / Reactivate, whichever applies — plus the Edit modal) used by both `pages/mera-admin/Users.jsx` and `pages/mera-admin/Institutions.jsx`. Both pages act on the exact same accounts via the exact same `PATCH /auth/admin/users/{id}/[deactivate|reactivate|]` endpoints, just surfaced from two different list views, so the component owns the whole interaction itself — menu open/close, the deactivate confirm + EMT-cascade-count alert, busy/error state, the edit modal — rather than each page reimplementing it. A page just renders `<UserRowActions user={row} onChanged={patch => ...} />` per row and merges whatever `onChanged` is called with into its own list state; `UserRowActions` reads `useAuth()` internally to work out `isSelf` on its own; it doesn't need to be told. Building this is what surfaced the `InstitutionSummarySerializer` gap noted above — without `is_active` in that response, every institution row would have shown "Deactivate" and never "Reactivate", regardless of its real state.

A related bug shipped in that same batch of work, caught and fixed the next session: `Institutions.jsx`'s Status column was still rendering `institutional_status` (approved/pending/rejected — a separate field from `is_active`, and one that's currently hardcoded to `"approved"` for every account in this prototype; see bypass #1 below) instead of `is_active`. Deactivate/reactivate only ever write `is_active`, never `institutional_status`, so the badge silently never moved — an admin could deactivate an institution from that page and it would keep reading "Approved" forever, even though `is_active` (and the account's actual ability to log in) had genuinely changed; `Users.jsx` showed the correct state the whole time since it was already reading `is_active`. Fixed by switching that column to `is_active`-based active/inactive, same as `Users.jsx`. Deliberately did **not** add `institutional_status` as a second column — it can't currently vary (every real account in this prototype is created with it hardcoded to `approved`), so a second column would just repeat an identical badge on every row; worth revisiting once the approval-gate bypass is reinstated and `institutional_status` becomes meaningful again. Verified against the real API, not just by reading the code: `is_active` was confirmed to flip `true → false → true` in `GET /auth/admin/institutions/`'s response across a real deactivate/reactivate cycle, while `institutional_status` stayed `"approved"` throughout.

**Login now actually checks `is_active` — a real gap, not one of the documented prototype bypasses below.** `accounts/views.py`, `LoginView` never checked `is_active` at all, for any role — this is separate from bypass #1 in the "Prototype safety bypasses" section, which is specifically about the *pending/rejected institutional-status* messaging block (still commented out, untouched). Nothing else covered plain deactivation either, so a deactivated account of any role could log in and receive a fully valid token. In practice this was less severe than it sounds: `djangorestframework-simplejwt`'s `JWTAuthentication.get_user()` already re-checks `is_active` on every *subsequent* authenticated request, so that token would fail on its very next real use regardless — but login itself still had no business returning 200 with real tokens for a deactivated account. Fixed: `LoginView` now returns 403 (`"This account has been deactivated. Contact your administrator."`) for `is_active=False`, checked before the still-bypassed institutional-status block. This fix was a precondition for the new reactivate endpoint to mean anything — "deactivate" needs to actually block access for "reactivate" to actually restore it. Side effect worth knowing about: `accounts/tests.py::LoginTest::test_pending_institutional_account_blocked` now passes — not because bypass #1 was re-enabled, but because that test's fixture also happens to set `is_active=False`, which this new, separate check now catches. The known-failure count dropped from 4 to 3 as a result; see "Known test suite gaps" below.
**Email OTP — second factor on top of patient login, not a replacement — new.** Per project scope, this only applied at first to the patient login flow (mobile); every other role (EMT, hospital_admin, ambulance_admin, mera_admin) kept logging in with just email/password. **Update: extended to EMT too — see below.** `LoginView`'s existing email/password verification (lock check, password check, `is_active` check, `reset_login_attempts()`) is untouched — the only change is what happens *after* those succeed: for a role requiring OTP, instead of returning `_token_response(user)` immediately, it now generates a 6-digit code (`accounts/models.py::EmailOTP` — same shape as `PasswordResetToken` above: a short-lived, single-use, user-scoped record consumed on use, just a 6-digit code meant to be typed rather than a long token meant to be a link), emails it via `send_mail` (first real outbound email in this backend — `PasswordResetRequestSerializer` above still only stubs sending), and responds `{"otp_required": true, "user_id": "<uuid>"}` instead of tokens. `POST /auth/verify-otp/` (`VerifyOTPSerializer`, styled after `PasswordResetConfirmSerializer` — a "verify a stored code, act on it" case, not credential-checking, so a serializer fit better here than inlining it in the view the way `GoogleSignInView` does) takes `{user_id, code}`, and only on a correct, unexpired, unused code does it return the same `_token_response()` every other login path uses. `POST /auth/resend-otp/` (`ResendOTPView`) takes `{user_id}` and issues a fresh code the same way login does, invalidating whatever code was live before (same "only one live code at a time" pattern `PasswordResetRequestSerializer` already uses for reset tokens — `EmailOTP.objects.filter(user=user, used=False).update(used=True)` before creating the new one).

  **Extended to EMT — new.** `accounts/models.py::OTP_REQUIRED_ROLES = {Role.PATIENT, Role.EMT}` (next to `HOSPITAL_ROLES`/`AMBULANCE_ROLES`, same module-level-set convention) replaces the three places that used to hardcode `role == Role.PATIENT`/`role=Role.PATIENT` for this specific feature: `LoginView`'s OTP-branch check, `ResendOTPView`'s user lookup, and `VerifyOTPSerializer.validate()`'s user lookup. All three now check `role in OTP_REQUIRED_ROLES` / `role__in=OTP_REQUIRED_ROLES` instead. Patient and EMT are grouped here not because they're otherwise treated alike (they aren't — EMTs don't self-register, patients do) but because both are mobile-only accounts a stolen device/session could otherwise fully compromise with just a password; every web-side role (hospital_admin, ambulance_admin, mera_admin, and the legacy hospital/ambulance_service names) has no equivalent mobile attack surface for this factor to protect and is genuinely unaffected — confirmed with dedicated tests for all three, not just one representative role, since the task named them individually. The underlying generation/rate-limit/guess-attempt mechanism (`_generate_and_send_otp`, `EmailOTP.attempts`/`OTP_MAX_VERIFY_ATTEMPTS`) was not touched and doesn't branch on role at all once the initial `role__in` lookup resolves a user — it was reused as-is, not duplicated, per the task's own instruction.

  **Mobile frontend needed zero logic changes — verified by actually reading the code, not assumed.** `login.tsx`'s `handleLogin()` branches only on the response's `otp_required` boolean, never on role; `verify-otp.tsx` posts `{user_id, code}`/`{user_id}` and calls the shared `routeAfterAuth(data.user.role)` helper on success — the same call every login path already made. `routeAfterAuth` (`mobile-frontend/utils/route-after-auth.ts`) already had an explicit `role === 'emt'` branch (routing to `/(ambulance)/active-response` or `/(ambulance)/dashboard`), built for the *non-OTP* EMT login path before this change — confirmed by reading that file directly rather than assuming "role-agnostic" meant "untested for this role." Only a handful of now-stale code comments in `login.tsx`/`verify-otp.tsx` said "patients only" and were corrected for accuracy; no behavior changed on mobile at all.

  **Tests:** `accounts/tests.py::EMTEmailOTPLoginTest` (3 tests, new — deliberately not a full duplicate of `EmailOTPLoginTest`'s 14: login sends OTP instead of tokens for an EMT with a real 6-digit code emailed; the correct code returns valid tokens via `VerifyOTPView`; resend actually works for an EMT — the one that would have silently 404'd before the fix, since `ResendOTPView`'s lookup was hardcoded to `role=Role.PATIENT`). The old single scope-boundary test (`test_non_patient_login_unaffected_by_otp`, which used an EMT as its "unaffected" example — now backwards) was replaced with three separate tests, one per still-unaffected role: `test_hospital_admin_login_unaffected_by_otp`, `test_ambulance_admin_login_unaffected_by_otp`, `test_mera_admin_login_unaffected_by_otp`. One pre-existing test also needed fixing as a direct consequence: `InstitutionReassignmentTest::test_reactivated_emt_can_actually_log_in_after_reassignment` logs in a real EMT through the actual endpoint and asserted immediate tokens — now correctly asserts it reaches the `otp_required` step instead (with Brevo newly mocked in that test, since it wasn't before — this EMT login previously never touched Brevo at all).

  **Gmail SMTP config** — `EMAIL_BACKEND`/`EMAIL_HOST=smtp.gmail.com`/`EMAIL_PORT=587`/`EMAIL_USE_TLS=True` in `settings.py`, `EMAIL_HOST_USER`/`EMAIL_HOST_PASSWORD` from env vars (the latter is a Gmail **app password**, not the account's real login password — Gmail requires this for SMTP when 2FA is on the sending account, and rejects the real password outright). Same "secrets never go in Git" rule as every other credential here.

  **Rate-limiting is two genuinely separate concerns, not one — both implemented, both tested.** Conflating them would leave a real gap either way:
  - **Generation throttling** (`_generate_and_send_otp()`, shared by `LoginView` and `ResendOTPView` — a resend-only limit would be a trivial bypass of the login-side one, so both call the same function): at most `OTP_MAX_PER_WINDOW` = 3 new codes per user per `OTP_GENERATION_WINDOW_MINUTES` = 10, checked by counting recent `EmailOTP` rows before creating another. This is about *sending volume* — generating a code sends a real email, so an unthrottled caller (or just a client bug looping resend) could spam a target's inbox or burn through this app's Gmail sending quota. 3-per-10-minutes is deliberately generous for the legitimate case (typo, letting a code expire, resending once or twice) while still bounding total volume to a handful, not unlimited. Exceeding it returns `429`, not a silent failure.
  - **Guess-attempt capping** (`EmailOTP.attempts`, checked in `VerifyOTPSerializer`): at most `OTP_MAX_VERIFY_ATTEMPTS` = 5 wrong guesses against a single live code before that code is burned (`used=True`) outright, forcing a resend rather than leaving it guessable indefinitely. This is about *brute-forcing a live code's 6-digit space* — a completely different attack shape than generation spam, and not something the generation limit does anything about (a code, once sent, would otherwise be guessable an unlimited number of times within its own validity window). Deliberately a **per-code** counter, not a per-user/permanent one — reusing `User.failed_login_attempts`/`is_locked` (the *password*-guess lockout) would conflate two unrelated failure modes and require an admin/password-reset intervention to recover from, when "request a new code" is the actually-appropriate recovery here.
  - Both are independent of `User.failed_login_attempts`/`is_locked`, which still means exactly what it always meant — password-guessing lockout, unaffected by anything OTP-related.

  **`EmailOTP.code` isn't cryptographically compared or hashed** (unlike `PasswordResetToken.token`, which is a 48-byte `secrets.token_urlsafe` value never meant to be guessed) — a 6-digit code is inherently guessable by design (that's the UX point, a human types it), so the real security property here is the guess-attempt cap above, not the code's own entropy. Generated via `secrets.randbelow(1_000_000)`, not `random`, matching this codebase's existing security-conscious convention (`PasswordResetRequestSerializer` already uses `secrets.token_urlsafe`).

  **Mobile.** `mobile-frontend/app/(auth)/verify-otp.tsx` — new screen, reached via `router.replace` (not `push`, so the back button can't return to a stale password-entry state and re-trigger login) from `login.tsx`'s `handleLogin` whenever the login response carries `otp_required: true`. A single 6-digit numeric `TextInput` (`keyboardType="number-pad"`, digits-only filter, `maxLength={6}`) rather than a segmented multi-box input — no existing precedent for the latter in this codebase, and building one wasn't warranted for a single screen. On successful verification: `saveToken()` then `routeAfterAuth(data.user.role)` — **the exact same two calls `handleLogin` always made**, just relocated to fire after the extra step instead of immediately; a patient's post-login destination (including the mid-emergency session-restore case `routeAfterAuth` already handles) is completely unaffected by the OTP step existing. Has its own "Resend" action calling `POST /auth/resend-otp/`, surfacing a `429` from the generation limit as-is (`"Too many verification codes requested. Please wait a few minutes and try again."`) since that's genuinely actionable information, not a generic failure message. **Deliberately not applied to Google Sign-In** (`useGoogleSignIn`, documented below) — this task's scope was specifically "on top of existing email/password login," and Google's own token verification is already a strong first-factor equivalent; whether OTP should also gate the Google path is a separate product question, not decided here.

  **Deployed backend OOM-killed on Render's free tier the day this + Google Sign-In shipped — root cause since CONFIRMED, and it was not memory exhaustion at all.** Symptom: `Worker (pid:X) was sent SIGKILL! Perhaps out of memory?` during patient login specifically. The investigation below happened in two passes — the first (measuring per-worker import-time memory cost) turned up a real but ultimately secondary finding; the second (walking gunicorn's actual source and the SMTP call itself) found the real cause. Both passes are kept here since both are genuinely instructive, not just the "winning" one.

  **Confirmed root cause: Render's free tier blocks all outbound SMTP ports (25, 465, 587) at the platform level.** This is a documented Render policy, not a bug in this app. The original Gmail SMTP integration (`django.core.mail.send_mail`, `EMAIL_BACKEND = smtp`) had no `EMAIL_TIMEOUT` configured, so every blocked connection attempt didn't fail fast — it hung, because Python's `smtplib` blocks indefinitely when nothing else sets a socket timeout. `_generate_and_send_otp()`'s `send_mail()` call also had no try/except around it, so a stuck worker just sat there, unable to service any other request. After `--timeout 30` (added as that session's mitigation), gunicorn's own arbiter would eventually notice the worker hadn't heartbeat in 30s and force-kill it — first `SIGABRT`, then `SIGKILL` if that didn't work (`gunicorn/arbiter.py::murder_workers()`, read directly from the installed package, not recalled from memory). Critically: gunicorn's `reap_workers()` logs **the exact same "Perhaps out of memory?" message for *any* SIGKILL death**, regardless of whether the OS's real OOM-killer did it or gunicorn's own timeout-enforcement did — the message is a heuristic guess based purely on which signal killed the process, not an actual memory reading. So the log line the team was chasing was real, but its own diagnosis ("perhaps out of memory") was gunicorn's guess, and the guess was wrong here.

  **Fix: switched OTP delivery from Gmail SMTP to Brevo's transactional email HTTP API** (`accounts/views.py::_send_otp_email`), since HTTPS (port 443) isn't blocked. Uses `requests.post()` directly against `https://api.brevo.com/v3/smtp/email` rather than Brevo's own SDK — `requests` was already an installed dependency (google-auth's transport pulls it in), so this added zero new packages. `BREVO_API_KEY`/`BREVO_SENDER_EMAIL` replace `EMAIL_HOST_USER`/`EMAIL_HOST_PASSWORD` et al. in `settings.py`; the Gmail SMTP settings were removed outright (not left dormant) — SMTP cannot work on this host at all, for any feature, so keeping those settings around would have been actively misleading. `PasswordResetRequestSerializer`'s still-stubbed email-sending comment was updated to point at Brevo too, so a future session doesn't repeat this exact mistake if that TODO ever gets picked up.

  This time, the exact gap that caused the hang was addressed directly, not just papered over: `_send_otp_email()` sets an explicit `timeout=10.0` on the `requests.post()` call (`BREVO_TIMEOUT_SECONDS`) — a slow/unreachable Brevo can now only ever fail *fast*, never hang the request — and the call is wrapped in `try/except requests.RequestException`, raising a small `OTPDeliveryError` that `LoginView`/`ResendOTPView` (via a shared `_otp_required_response()` helper) turn into a clean `503 "Could not send verification code. Please try again shortly."` instead of an unhandled exception. `_generate_and_send_otp()` was also reordered while this was being fixed: it now **sends the email first, and only invalidates the old code / persists the new one if that send actually succeeds** — the original ordering (persist-then-send) meant a failed send under the old code left a patient with no valid code at all (old one already invalidated, new one never delivered); sending first means a delivery failure leaves whatever code the patient already has untouched. Covered by `test_otp_delivery_failure_returns_503_and_leaves_existing_code_usable` and `test_otp_delivery_http_error_returns_503` in `EmailOTPLoginTest` above.

  **The earlier memory investigation wasn't wasted effort, but its top-line conclusion doesn't hold as the primary cause — corrected here rather than left standing.** The measured **+9.5MB per worker from importing google-auth/cryptography/requests at module level** (via `ctypes`-based `GetProcessMemoryInfo`, in-process before/after import) is still an accurate, real measurement — that part wasn't wrong. What was wrong was treating it as *the* explanation for the SIGKILL pattern. It's a real, minor, still-unaddressed inefficiency (lazy-importing `google.auth` only inside the view that needs it would claw most of it back), but it is not what was crashing patient login — the hung SMTP connection was. Worth remembering for next time: a plausible, measured contributor found through code inspection isn't the same as a confirmed root cause; this got corrected here once the actual mechanism (SMTP port block → hang → gunicorn's own timeout-kill) was found and verified against gunicorn's real source, not before.

  **`--workers 1` (that session's mitigation) has been reverted — it was never the actual fix, and unnecessarily limited concurrency once the real fix landed.** `Procfile` now reads `--workers 2 --timeout 30`. Chosen from the same measured baseline as above: `~60.3MB` per worker (Django + DRF + the google-auth/cryptography/requests chain) × 2 ≈ **~121MB**, leaving a comfortable margin under the 512MB ceiling once the gunicorn master process, Postgres connection overhead, and actual request-time memory are accounted for — safer than the original unset default (which scales off the *host's* CPU count, not the container's memory budget, and could easily have meant 3-5+ workers). `--timeout 30` is kept — it's a reasonable general safety net against *any* stuck request, not specific to the SMTP issue, and is now genuinely just a backstop rather than the only thing standing between a hang and the whole service going down.

  **Anti-enumeration — the part that needed real care, because it has three outcomes to hide, not two.** `validate_email()` already never rejected an unrecognized email (pre-existing, unchanged) and the view already always returned the same 200 (pre-existing, unchanged) — but wiring up a *real* email send introduced a third case the old, do-nothing version never had to handle: what happens when the account is real but Brevo itself fails? `TriggerPasswordResetView` (admin-facing, no enumeration concern — the admin already knows the target account exists) correctly returns a `503` on delivery failure, telling the admin to retry. Doing the same here would be a real leak: a `503`-only-for-real-accounts response distinguishes "this email exists" just as surely as an explicit "no account found" message would.   **Per-target-email rate limit on self-service generation — closes a gap flagged (not fixed) in an earlier session.** `PasswordResetRequestView` is unauthenticated and sends a real email, but originally had no bespoke rate limiting beyond the general `anon` throttle default (30/min, IP-keyed — see "API rate limiting" below) — which bounds "how many requests can one IP make," not "how many reset emails can one target inbox receive." A caller spreading requests across IPs could otherwise spam one victim's inbox indefinitely. Fixed with `accounts/views.py::_password_reset_generation_allowed(user)`, deliberately reusing the exact same shape `_generate_and_send_otp()` already established for `EmailOTP` (count recent rows for this user within a window, cap at N) rather than inventing a second mechanism — `PASSWORD_RESET_MAX_PER_WINDOW = 3` per `PASSWORD_RESET_WINDOW_MINUTES = 60`, counting `PasswordResetToken` rows (which, same as `EmailOTP` rows, are only ever created after a send has actually succeeded — a Brevo failure never counts against the budget, and neither does a request that was itself rate-limited).

  **Why 60 minutes, not OTP's 10 — the window is matched to the thing it's protecting, not copied wholesale.** A forgotten password is a much lower-frequency event than a login code needed on every session, and the token this gates is valid for a full hour (`issue_password_reset_token`), an order of magnitude longer than a 5-minute OTP code — a short window would let the counter reset while the *previous* link is still perfectly usable, which doesn't match how someone would actually retry ("my email didn't arrive, let me try again" makes sense minutes apart; it doesn't make sense to reset the counter while an unexpired link from 12 minutes ago is still sitting in their inbox). Matching the window to the token's own lifetime means "at most 3 fresh links per hour per account" — generous for every legitimate retry (typo'd the email, checking spam, wanting a fresh link before the old one expires) while bounding an attacker to a handful of emails per hour against one target, regardless of how many IPs or requests they spread the attempts across. No separate guess-attempt concern exists here the way OTP has one (`EmailOTP.attempts`/`OTP_MAX_VERIFY_ATTEMPTS`) — a reset token is a long, unguessable `secrets.token_urlsafe(48)`, not a 6-digit code meant to be typed, so generation volume is the only axis worth bounding.

  **Must not become a new enumeration vector — the actual hard part.** Before this fix, the endpoint's anti-enumeration contract had to hold across three outcomes (no account / real account, sent / real account, send failed); the rate limit adds a fourth (real account, but already at its generation cap this hour), and all four still return the exact same `200` with the exact same generic message. The alternative — a `429` or any other distinguishable response once the limit hits — would itself leak the thing this endpoint exists to hide: it would confirm the address is real (only real accounts can hit a *generation* cap at all) and, worse, that it had actually been receiving emails right up until it suddenly stopped. `PasswordResetRequestView.post()`'s existing `if user is not None:` gate simply grew a second condition (`and _password_reset_generation_allowed(user)`) — when either is false, the request silently no-ops and falls through to the same `return Response(...)` every other case already used; no new branch, no new response shape.

  **A residual, pre-existing limitation, not introduced by this fix:** a rate-limited request skips the real Brevo network round-trip entirely, the same way a nonexistent-email request always has — so a sufficiently precise timing measurement could in principle distinguish "no network call happened" from "one did." This timing side-channel already existed for the nonexistent-email case before this session and is unchanged by adding the rate limit; not addressed here (would need artificial constant-time delays on every branch of this view, which wasn't asked for and adds real latency to the legitimate path for a fairly marginal hardening gain).

**API rate limiting (DRF throttling) — new.** A prior investigation found this API had **zero general request-frequency protection anywhere** — no `DEFAULT_THROTTLE_CLASSES`/`DEFAULT_THROTTLE_RATES` in `settings.py` (DRF's throttling framework was simply never configured, despite already being part of `djangorestframework`), no `django-ratelimit` or similar, nothing. The only existing protections were narrow and feature-specific: login lockout after 5 wrong passwords (`User.failed_login_attempts`/`is_locked`), and the OTP generation/guess-attempt limits (`OTP_MAX_PER_WINDOW`, `OTP_MAX_VERIFY_ATTEMPTS` — see the Email OTP section above).   **General baseline**, `settings.py`'s `REST_FRAMEWORK`: `DEFAULT_THROTTLE_CLASSES = [AnonRateThrottle, UserRateThrottle]` with `DEFAULT_THROTTLE_RATES = {"anon": "30/min", "user": "100/min"}`. Chosen generously enough not to interfere with normal usage — this app polls several mobile screens every 10-15s (see "Live location tracking" under the `emergencies` app section below), so a single active session can easily produce a handful of requests per minute — while still bounding a tight-loop spam script to a fixed ceiling instead of unlimited.

  **Two stricter named scopes**, via DRF's `ScopedRateThrottle` (`throttle_classes = [ScopedRateThrottle]` + `throttle_scope = "..."` on the view, which replaces the general default for that view rather than stacking with it):
  - `"password_reset_trigger": "5/hour"` — `TriggerPasswordResetView` only. Sends a real Brevo email per call; same "an unthrottled caller could spam a target's inbox or burn through sending quota" concern `_generate_and_send_otp`'s own comment already reasons about for OTP, just previously unprotected here.

Each triggers one or more real Cloudinary upload calls. Deliberately **one shared scope across all three**, not three separate ones: `ScopedRateThrottle`'s cache key is `(scope, caller)` only, not the specific view/URL, so a MERA admin splitting calls across the two creation endpoints still hits one combined ceiling — matching the actual thing being bounded (shared Cloudinary quota), not a per-endpoint-type quota that would be trivially sidestepped by alternating endpoints.

  **`POST /incidents/trigger_sos/` deliberately did NOT get a bespoke throttle scope** — see "SOS duplicate-prevention" under the `emergencies` app section below for the reasoning; it's covered by the general `user` default like every other authenticated endpoint, which is sufficient once that fix is in place.

  **Known limitation, not fixed here:** throttle state lives in `CACHES` (`LocMemCache`, no Redis — see below), which is per-process. This is **not** shared across gunicorn's `--workers 2` on Render, so a client's effective ceiling in production can be up to ~2x whatever's configured, depending on which worker handles each request. Not addressed (would need a shared cache backend like Redis, which this prototype deliberately doesn't run) — the rates above are chosen generously enough that this doesn't undermine their purpose (stopping unbounded spam, not enforcing an exact quota).

  **A real, observed gotcha while building this — CACHES now switches to `DummyCache` during `manage.py test`.** Enabling throttling for real initially broke a large chunk of the *existing* test suite (19 failures, 1 error) with no code-behavior bug involved at all: Django's test client sends every request in an entire test run from the same fake IP, so the anonymous throttle's IP-keyed bucket accumulated across many unrelated test classes (logins, Google sign-in, password-reset requests, etc.) and started returning `429` for tests that had nothing to do with throttling — which then cascaded into further failures (e.g. a login blocked by `429` never reaches `record_failed_login()`, so a lockout test sees `failed_login_attempts` stuck at 0). Lowering the rate via `@override_settings(REST_FRAMEWORK=...)` does **not** fix this and can't: DRF's `SimpleRateThrottle.THROTTLE_RATES = api_settings.DEFAULT_THROTTLE_RATES` is a plain class attribute bound once, at import time — reassigning the Django setting later doesn't retroactively change it (a real, documented DRF testing gotcha, not a mistake in this codebase's config). Fixed instead by switching `CACHES` to `django.core.cache.backends.dummy.DummyCache` specifically when `"test" in sys.argv` — a cache that implements the full API but never actually stores anything, so every throttle check sees "no prior requests" and always allows, equivalent to throttling being off, without touching the throttle configuration itself. `accounts/tests.py::ThrottlingTest` (the one place that actually needs real throttling behavior to test it) opts back into a real cache via its own class-level `@override_settings(CACHES={"default": {"BACKEND": "...LocMemCache"}})` — Django's cache *backend selection* (unlike DRF's frozen rate dict) genuinely is `override_settings`-aware.

**SOS duplicate-prevention on `POST /incidents/trigger_sos/` — new, chosen over a rate limit.** An investigation into request-frequency protection found `trigger_sos` had none at all — no throttle, and `services.trigger_sos()` unconditionally created a brand-new `Incident` on every single call, with no check for one already in progress. The fix here is a business-logic duplicate check, not a throttle, and that was a deliberate judgment call: a rate limit only stops *excessive* spam, but the actual failure mode that matters most here is a single accidental double-tap — a patient under stress with shaky hands, a slow UI response tempting a second press, a flaky connection triggering a client-side retry. A double-tap a second apart is well within any generous per-minute ceiling a rate limit would set, so a rate limit alone would not have prevented it. And two `Incident`s for the same emergency is a real correctness bug regardless of intent behind it — it could mean two ambulances dispatched to one patient, and emergency contacts notified twice for a single event. A rate limit would only ever have been a mitigation for the abuse case; the duplicate check actually fixes the correctness problem, and incidentally neutralizes most of the abuse concern too (repeated calls just cheaply return the same existing incident rather than creating garbage rows), which is why `trigger_sos` deliberately did **not** also get a bespoke `ScopedRateThrottle` scope — see "API rate limiting" under the `accounts` app section above. The general `user` default (100/min) still applies to it like any other authenticated endpoint, as a baseline against a different, cruder abuse shape (raw request-volume flooding) that the duplicate check doesn't address by itself.

When the route call is unavailable or fails, **no line is drawn at all** (not even a straight-line fallback) — both markers still render — per the explicit spec ("the map should still show both markers even without a route line"). Distance/ETA are shown in the existing address-row strip beneath the map, replacing "📍 Patient location shared" with e.g. "🚗 2.3 km away • ETA 6 min" whenever a route is available.

  **Route-call throttling — reasoning.** `GET /incidents/{id}/route/` cost real Google Routes API quota per call (see the pricing-tier note above), so it is deliberately *not* called on every 12s location tick — that would be ~5x more calls than useful, since a route recomputed after the ambulance moved 20m isn't meaningfully different from the last one. Instead `maybeFetchRoute()` combines two independent gates: a **distance gate** (only recompute once the EMT has moved ≥150m since the last route call's origin) combined with a **30s floor** (never call more often than that even if moving fast — e.g. on a highway, 150m can pass in a few seconds), and a **60s ceiling** that forces a recompute regardless of movement or the 30s floor. The ceiling isn't about the route actually changing while stationary — this project's Basic-tier Routes API call doesn't factor live traffic, so a genuinely stationary position's route/ETA wouldn't change — it's a resilience/retry mechanism: if the last call failed (network hiccup, transient 503 from the backend's own Google-failure handling), this guarantees another attempt within a bounded time instead of only retrying whenever the EMT happens to move 150m. Net effect at typical urban ambulance speed: a route call roughly every 30-60s rather than every 12s, without ever leaving the ETA more than a minute stale. The patient-side screen reuses this exact same reasoning and these same constants (150m/30s/60s) — see "Real route polyline (patient side) — done" above.

  **Three real bugs found in live device testing, fixed in a follow-up pass.**

  1. **ETA never resolved — the real value was fetched and simply never displayed.** `emergency-active.tsx`'s "Calculating ETA..." text was bound to `incident.eta_minutes`, not `route.duration_seconds` — a completely different field: `eta_minutes` is only ever set by `select_destination_hospital()` when the EMT notifies a hospital (the ambulance's ETA *to the hospital*, not to the patient), and even then it's a hardcoded literal (`active-response.tsx`'s `handleNotifyHospital()` always sends `eta_minutes: 8`, not a computed value). The raw id fields are left in place alongside the new name fields (existing truthy-checks like `if (incident.ambulance_service)` don't need to change, and something might legitimately want the id later). `emergency-active.tsx` now reads `ambulance_service_name`/`destination_hospital_name`. **`emergency-history.tsx` had the identical bug** (same `IncidentPatientSerializer` backs `GET /incidents/`, the list endpoint that screen calls) — fixed there too for the same reason fixing the serializer without it would've been a half-finished rename.

  3a. **Map camera never re-framed to show both markers.** Both `emergency-active.tsx` and `active-response.tsx` used `MapView`'s `initialRegion` prop exclusively — react-native-maps only reads this once, at mount; changing the underlying coordinates afterward does nothing. Camera locked onto whichever coordinate was known first (patient's SOS location on the patient screen; patient-or-own location on the EMT screen) with a tight `0.05°` delta, and never adjusted once the second marker appeared later — plausible to be well outside that initial viewport for a dispatched-from-a-distance ambulance. Fixed by adding a `mapRef` + `fitToCoordinates([...], { edgePadding, animated: true })` call (react-native-maps' actual imperative API for this) on both screens, triggered by a `useEffect` gated on both coordinates being known. Re-fit is gated on real movement — **reuses the exact same 150m `ROUTE_RECALC_DISTANCE_METERS` threshold already defined for route-call throttling** on each screen, rather than inventing a second magic number — so the camera doesn't jump on every single GPS-jitter poll (which would be as distracting as never moving, and would fight anyone manually panning/zooming), but does reliably reframe once either party has moved meaningfully. Depends on the *raw* incoming coordinates (`ambulanceTarget`/`myLocation`), not their `useSmoothCoordinate`-eased display values, which change every animation frame and would otherwise re-fire the effect continuously during each 1.5s marker glide instead of once per real GPS update.

  3b. **Route fetch producing no visible polyline, confirmed by real two-device testing to genuinely have no line rendered (not just off-screen — 3a is a separate bug from this one, verified independently before assuming they shared a cause).** Investigated the actual render path carefully rather than assuming: `decode-polyline.ts`'s algorithm was hand-traced byte-by-byte against the standard Google polyline decode (it uses a differently-derived but mathematically equivalent bit-unpacking trick — `result` starts at `1` instead of `0` and each byte is read unmasked as `charCode - 64` instead of `(charCode - 63) & 0x1f`; verified this produces identical output for both single-byte and multi-byte/continuation cases) — **not the bug**. `<Polyline coordinates={routePoints} .../>` uses the correct prop name and the `Coordinate` shape (`{latitude, longitude}`) matches exactly what `decodePolyline()` returns — **not the bug**. What *is* a real, confirmed gap: the backend's `route` view returns `{"available": True, **route_data}` on success, but if Google's response ever comes back without a usable `polyline` field (`get_route()`'s `"polyline": (route.get("polyline") or {}).get("encodedPolyline")` — silently `None` if the shape doesn't match expectations), the response is still `available: true`, just with `polyline: null` — and the frontend's old `route?.available && route.polyline ? decodePolyline(...) : []` treated that identically to "no route needed yet, nothing to show," with zero signal anywhere that a fetch had actually happened and come back empty. This wasn't fixed (root cause on the Google/response side wasn't reproducible from the repo alone), but it's no longer silent: both screens now track `routeUnavailable = !!route && (!route.available || routePoints.length < 2)`, distinct from `route === null` (genuinely not fetched yet), and surface it visibly on-device — a warning banner on `emergency-active.tsx`'s map, and an upgraded `addressRow` message on `active-response.tsx` (previously that row only ever showed real route info or a generic "Patient location shared" fallback, with no way to tell "haven't tried yet" from "tried and got nothing" — now it does). Next real test should make it possible to tell, from the device alone with no dev tools attached, whether this is the missing-deployed-`GOOGLE_MAPS_API_KEY` theory, a Google response-shape mismatch, or something else — narrowing that down is the next step, not done here.

**Session-restore on app launch (SC-01) — new.** Real gap found on investigation, not just a missing nicety: the mobile app had **no app-launch auth check of any kind**. `(auth)/index.tsx` (the actual route-tree root — confirmed by its file position, not just by name) was a fully static splash screen; it never read the stored token, never called `/auth/me/`, nothing. Every cold start — even for an already-logged-in user with a stored token — showed the "Login / Register" splash and required logging in again manually. This is a stronger gap than "checks token+role but not incident status" (the assumption the investigation started from) — there was no restore-of-any-kind to build on, so this fix had to add the whole thing, not just extend an existing check.

Two pieces:
- `GET /incidents/my_active/` (`emergencies/views.py`) — new, small, role-aware endpoint: for a patient, the most recently triggered incident that isn't `COMPLETED`/`CANCELLED` (`.exclude()` on those two rather than an include-list, so a future new intermediate status is automatically covered); for an EMT/ambulance (`AMBULANCE_RESPONDER_ROLES`, resolved through `effective_ambulance_service` same as everywhere else), the equivalent query scoped to `ambulance_service=account`. Returns `{"active_incident": <serialized incident> | null}`. **Deliberately conservative on the ambulance side:** `Incident.ambulance_service` is service-level, not per-EMT (see the EMT-attribution note below — the data model doesn't track which individual EMT is on which incident), so if a service has multiple EMTs each mid-response on a *different* incident at once, this endpoint can't tell which one belongs to the requesting EMT specifically. Rather than guess (which could silently route an EMT into a colleague's response for a different patient), it only returns a match when there's **exactly one** non-terminal incident for that service — two or more is treated as ambiguous and returns `null`, falling back to the normal dashboard. Covered by `emergencies/tests.py::MyActiveIncidentTest` (14 tests — patient found/not-found/most-recent-wins/not-leaked-to-other-patients, ambulance found/not-found/the-two-concurrent-ambiguous-case, EMT resolution through `effective_ambulance_service`, orphan EMT with no linked service, unrelated ambulance not shown someone else's incident).
- `mobile-frontend/utils/route-after-auth.ts` — new shared `routeAfterAuth(role)` helper: calls `my_active` and `router.replace()`s to `emergency-active`/`active-response` with the found incident's id if there is one, otherwise to the role's normal dashboard. Shared by **both** `(auth)/index.tsx`'s new session-restore check (added: on launch, if a stored token still verifies via `/auth/me/`, call `routeAfterAuth` instead of showing the splash; no token or a token that no longer verifies — expired/deactivated/network failure — clears tokens and falls through to the normal splash) and `login.tsx`'s post-login redirect (previously its own separate inline if/else role table — replaced with a call to the same helper). Deliberately shared rather than duplicated: a patient whose app reloads mid-emergency and a patient who gets logged out and logs back in mid-emergency should land in the same place via the same logic, not two independently-maintained copies of it that could drift.

**EMT incident attribution — fixed.** `accounts/models.py` now has `User.effective_ambulance_service`: returns `self.ambulance_service` (the linked ambulance_admin) for an EMT, or `self` for every other role. This is the single resolution point used everywhere an incident's ownership is checked or set, replacing five separate spots that previously compared directly against `request.user`: `emergencies/views.py` `get_queryset()`, `_get_assigned_incident()` (shared by `select_hospital`/`update_status`/`treatment_notes`), `accept()`, `my_responses()`, and `emergencies/permissions.py`'s `IsAcceptingAmbulance`. `services.accept_incident()`'s signature changed from `accept_incident(incident, ambulance_user)` to `accept_incident(incident, ambulance_service, actor)` — `ambulance_service` is the resolved institution account written to the FK, `actor` is the real user recorded on the audit log (so an EMT's name still shows up in `EmergencyLog`, even though the incident itself attributes to their ambulance_admin). Net effect: an EMT accepting an incident now correctly makes it show up in their ambulance_admin's `my_responses`/dashboard stats, any EMT on the same crew (not just whoever originally accepted) can view `medical_detail` and act on it, and an EMT with no linked `ambulance_service` gets a 400 instead of a crash. **NFC emergency tags — new.** A business-sold physical tag that, when tapped by a bystander, opens a public web page that can trigger an SOS on behalf of the patient it's paired to. **This is a new trigger SOURCE for the existing incident pipeline, not a new incident type or a parallel code path** — the public trigger endpoint calls the exact same `services.trigger_sos()`/`confirm_sos()` functions the authenticated mobile SOS button uses, just with `activation_method="nfc_bystander"` instead of `"manual"`, so every downstream consequence (emergency-contact SMS, hospital selection, EMT dispatch, ...) is unchanged and covered by the same tests that already cover a normal SOS.

  **Business model:** tags are manufactured/sold as pre-paired inventory. A MERA admin generates a batch of tokens in the dashboard, someone writes each token's URL onto a physical NFC sticker **outside this app** (a free NFC-writing app — not this codebase's concern), and later, when a tag is actually sold/issued to a patient, an admin pairs that specific physical tag to their account via its short code.

  **Model — placed in `emergencies`, not a new app.** `NFCTag` (`emergencies/models.py`) is tightly coupled to `Incident`/`ActivationMethod`/`services.trigger_sos()`/`confirm_sos()` — the public trigger endpoint calls those services directly — so keeping it in `emergencies` avoided a new cross-app dependency the way a standalone app would have needed. `token` (long, unguessable, `secrets.token_urlsafe(32)`) is the value in the public URL (`WEB_FRONTEND_URL/nfc/<token>`); `short_code` (8 chars, uppercase alphanumeric with visually-confusable characters `0/O/1/I/L` excluded) is what an admin reads off a physical sticker and types in to pair it, since a browser-based admin panel can't scan NFC directly; `patient` is a nullable FK to `User` (null = unpaired inventory) with `paired_at` set alongside it. `Incident.ActivationMethod` gained `NFC_BYSTANDER = "nfc_bystander"`, and `Incident.activation_method`'s `max_length` was widened from 10 to 20 to actually fit it (the field only ever needed to hold `manual`/`auto`/`offline` before). Migration: `emergencies/0004_alter_incident_activation_method_nfctag.py`.

  **MERA admin dashboard** (`web-frontend/src/pages/mera-admin/NFCTags.jsx`, new nav item in `MeraAdminLayout.jsx`), backed by three new `IsMERAAdmin`-gated endpoints in `emergencies/views.py`/`urls.py`: `POST /nfc-tags/generate/` (batch-create N unpaired tags, returns short codes + full URLs so the admin can note/print them before writing physical stickers — shown once in a modal, but also findable afterward in the list below, same "don't reshow a secret twice" reasoning `Institutions.jsx`'s own account-creation flow already follows for passwords); `GET /nfc-tags/?paired=true|false` (list, optionally filtered); `POST /nfc-tags/pair/ {short_code, patient_id}` (`services.pair_nfc_tag` — rejects an already-paired tag and an unrecognized short code with distinct messages, matching this codebase's existing "clear, specific field error, not a generic 400" convention). Patient search/select in the pairing modal reuses `GET /auth/admin/users/?search=` filtered client-side to `role === 'patient'` — same pattern `Institutions.jsx`'s `successor_of` reassignment dropdown already uses for a role-filtered list, since `AllUsersListView` has no server-side role filter of its own.

  **Public, unauthenticated backend endpoints** (`emergencies/views.py` — `NFCTagStatusView`/`NFCTagTriggerView`, both `permission_classes = [AllowAny]` with `authentication_classes = []`, since `REST_FRAMEWORK`'s `DEFAULT_PERMISSION_CLASSES` is `IsAuthenticated` globally): `GET /nfc/<token>/` returns `{"status": "invalid" | "unpaired" | "paired" | "active_incident"}` — deliberately a bare status string and nothing else (`services.nfc_tag_status`), never the patient's name or any medical/incident detail, checked by a dedicated test that asserts the response's key set is exactly `{"status"}`. `POST /nfc/<token>/trigger/` (`services.trigger_nfc_sos`) rejects an unpaired tag (400) and a patient who already has a non-terminal incident (409) — the latter deliberately **reuses `trigger_sos()`'s own `(incident, created)` duplicate-prevention return value** rather than a second copy of that query: `created=False` is turned into an explicit rejection here instead of the silent 200-with-existing-incident the authenticated patient-facing endpoint returns, since the public endpoint must never echo incident/patient data back to an anonymous caller either way, and a bystander reaching this branch already saw `"active_incident"` from the GET status check before tapping confirm. A successful trigger responds `{"detail": "Help has been alerted."}` — no incident id, no patient data.

  **Per-token rate limiting — the accepted residual risk.** `NFCTagTriggerThrottle` (`ScopedRateThrottle` subclass, `throttle_scope = "nfc_trigger"` on the view, `"nfc_trigger": "5/hour"` in `settings.py`) overrides `get_cache_key()` to key on the URL's `token` kwarg instead of DRF's default IP-based anonymous key — a leaked or photographed token URL could otherwise be replayed indefinitely from many different callers/IPs, which a per-IP throttle wouldn't catch at all. **This bounds the abuse, it doesn't eliminate it**: up to 5 trigger attempts per token per hour still get through regardless of who's calling, and — same caveat as every other rate limit in this app (see "API rate limiting" above) — the throttle cache is `LocMemCache` (no Redis), per-process, so the real ceiling in production can be up to ~2x this under gunicorn's `--workers 2`. **Accepted as a residual risk for this prototype's scope, at the same tier as the three documented "Prototype safety bypasses" below** — not hardened further (no CAPTCHA, no single-use/burn-after-use token rotation, no device fingerprinting). A subtlety worth remembering if this throttle is ever copied elsewhere: `ScopedRateThrottle.allow_request()` reads `view.throttle_scope` (not the throttle class's own `scope` attribute) to decide the rate and to set `self.scope` before `get_cache_key()` runs — omitting `throttle_scope` on the view makes `allow_request()` silently return `True` for every request, which is exactly what happened on the first pass here before the tests caught it.

  **Public web-frontend page** — `web-frontend/src/pages/public/NFCTrigger.jsx`, route `/nfc/:token`, registered in `App.jsx` outside `ProtectedRoute` (no login required, matching `/reset-password`/`/terms-and-conditions`). Self-contained dark styling using the mobile app's own emergency-red/success-green palette (`Colors.emergency`/`Colors.success` from `constants/theme.ts`) rather than the lighter `--mera-accent` blue the login/admin pages use — deliberately meant to read as "the SOS screen," not "a MERA form." States: invalid tag, not-yet-activated (unpaired), already-alerted (`active_incident`), the hold-to-confirm button (`paired`), success, and a generic retry error. **Hold-to-confirm, not a single tap** — mirrors `patient-dashboard.tsx`'s own `onPressIn`/`onPressOut` + 1.5s `setTimeout` interaction exactly (same duration, same "cancel the timer on early release" logic, translated to `onMouseDown`/`onTouchStart` for the web), specifically to avoid a tag brushed against a pocket or bag firing a real alert. After a successful trigger, shows only "Help has been alerted" — no patient-identifying info anywhere on this page, per the original design decision; the backend's response never gives it anything to show anyway.

  **Mobile — patient-side visibility.** Investigated first, not assumed: `GET /incidents/my_active/` was **not called from `patient-dashboard.tsx` at all**, mount or poll — the only existing caller anywhere in the mobile app was `utils/route-after-auth.ts`'s `routeAfterAuth()`, used at app launch (`(auth)/index.tsx`) and right after login (`login.tsx`), same as the "Session-restore on app launch" feature above already documents. ## Key architectural decisions already made (don't relitigate without discussion)

1. **AI calls are backend-only.** The Django `chatbot` app calls Anthropic's API server-side. The API key lives only in the backend's environment variables, never in either frontend.
2. **Chatbot consent is separate from data-sharing consent.** A patient can consent to sharing data with hospitals/ambulances without consenting to the AI chatbot using their profile as context, and vice versa.
3. **Chatbot responses are structured JSON**, not freeform text, so the frontend can reliably show a "consult a professional" banner without relying on string-matching the AI's wording.
4. **The chatbot does not autonomously trigger SOS or suggest emergency dispatch.** It can flag that a response touches on something serious (`needs_referral`), but never decides to call an ambulance — that stays a deliberate, manual action by the patient (same press-and-hold safety gesture as the main SOS button).
5. **One web app, not three.** Hospital Admin, Ambulance Admin, and MERA super-admin all log into the same web app at the same URL. The UI shown after login depends on the logged-in user's `role` — this is not three separate deployed applications.
6. **Secrets never go in Git.** `.env` files are gitignored in every project folder. Real secrets are shared between teammates privately (not via GitHub, Slack, or Discord in plaintext).

## Prototype safety bypasses — MUST be reinstated before any real launch

Running the Django test suite (`python manage.py test`) surfaced three places where real safety/verification logic has been deliberately disabled for prototype/demo purposes. These are not bugs — they were intentional shortcuts — but they mean the current prototype is **not safe to use with real patient data or real institutions.** Anyone touching auth, SOS, or medical profile verification should know these exist:

1. **Institutional account approval gate is bypassed.** `accounts/views.py`, `LoginView` — the check that blocks `pending`/`rejected` hospital and ambulance accounts from logging in is commented out (`# PROTOTYPE: approval gate bypassed; reinstate for production`). Right now, any institutional account can log in regardless of MERA approval status. (This is specifically about the pending/rejected *institutional-status* messaging. A separate, general `is_active` check exists in the same view and is *not* bypassed — see "Login now actually checks `is_active`" under the `accounts` app section above.)

2. **Patient SOS verification check is hardcoded to always pass.** `emergencies/services.py`, `_patient_is_verified()` — this function unconditionally `return True`s instead of actually checking the patient's verification status. Any patient, verified or not, can currently trigger a real SOS.

3. **Medical profile auto-verifies on submission instead of requiring hospital review.** `medical_profiles/models.py`, `submit_by_patient()` — sets `verification_status = VERIFIED` immediately instead of `PENDING` (comment: "Auto-verified for prototype — skipping hospital verification flow"). The hospital verification queue (SC-12/SC-12b) currently has nothing real to review.

**Before any real-world use, all three of these need to be re-enabled and tested.** Until then, treat every patient/institutional account in this system as unverified in practice, regardless of what their `verification_status` field says.

   **Visibility-aware polling — added in a follow-up session.** A plain `setInterval` poll is silently throttled by the browser once its tab is backgrounded (Chrome in particular can push a 15s interval out to minutes), so a hospital admin who alt-tabs away and back could sit on a stale list far longer than 15s with no indication anything was wrong. Fixed by listening for `document.visibilitychange`: on `hidden`, the interval is `clearInterval`'d outright rather than left to be throttled; on becoming visible again, `load(false)` fires immediately (the list is presumed stale by however long the tab was away) and the interval is restarted fresh via a `startPolling()` helper, so the next tick is 15s from the moment the tab came back, not whenever the old (paused) schedule would have landed. Verified with real headless-Chromium (CDP) automation, not just code review: simulated a tab going hidden for 20s (confirmed zero requests fired, vs. the pre-fix behavior of the interval free-running/getting throttled unpredictably), then simulated it becoming visible again and confirmed a GET fired within ~60ms plus a correctly-spaced next poll ~15s later. **If `VerificationQueue.jsx` or either `Dashboard.jsx` (see the "Lower priority" staleness note below) get polling added, apply this same hidden/visible pattern rather than a bare `setInterval` — it's a small addition (one `useEffect`-scoped event listener) and avoids reintroducing the same background-tab staleness bug there.**

   **Debugging gotcha worth remembering:** don't count raw `Network.requestWillBeSent` events (or entries in the browser's Network tab) as "number of API calls made." Every cross-origin call from this app (frontend on `:5173`, backend on `:8000`) that carries the `Authorization` header — i.e. basically every `apiCall()` — is a CORS "non-simple" request, so the browser fires an `OPTIONS` preflight immediately before the real request. That preflight is a separate network-level entry for the *same* URL, and the browser also skips it on subsequent identical calls once the preflight result is cached (`Access-Control-Max-Age`), so counts can look inconsistent call to call. A prior investigation session miscounted this way and concluded `IncomingAmbulances.jsx` was firing "4 duplicate requests" on mount; a rigorous re-test with console-level instrumentation (counting actual `apiCall()`/`fetch()` invocations, not network-level entries, and filtering by HTTP method) confirmed the real number was the expected React-StrictMode-doubled 2 in dev (1 in production) — there was no extra application bug. If a network-request count ever looks off by a clean multiple of 2, check for preflights before assuming duplicate fetch logic.

   **2. Frontend is blocked by a real ecosystem constraint.** Google OAuth's "Web application" client type — the client type `expo-auth-session`'s browser-redirect flow relies on — requires every redirect URI it's configured with to be a real, public-domain URL. Expo Go's own dev-server redirect (`exp://<local-ip>:<port>/--/...`, generated fresh per machine/network by `AuthSession.makeRedirectUri()`) is neither public nor stable, and Google rejects it outright — this isn't a misconfiguration on this project's end, it's Google's own client-type restriction. Expo used to offer a hosted proxy (`auth.expo.io`) specifically to work around this by giving apps a stable public redirect URL, but **that proxy service is now deprecated** and can't be relied on. The fix documented by the wider Expo/Google developer community is to stop using the web-based OAuth flow entirely and switch to Google's own native sign-in library, `@react-native-google-signin/google-signin` — but that library **explicitly cannot run inside Expo Go at all**; it requires a custom Expo development build (`expo prebuild` / `eas build --profile development` or equivalent) to test, which this project doesn't have set up (the whole mobile dev workflow so far has been plain `expo start`/Expo Go — see the Tech stack section above).

   **Backend — `POST /auth/google/`** (`accounts/views.py::GoogleSignInView`, `accounts/serializers.py::GoogleSignInSerializer`). Accepts `{id_token, popi_consent?, terms_consent?}`. Verification uses Google's own library (`google-auth`, newly added to `requirements.txt` along with `requests` — the standard companion package its documented transport, `google.auth.transport.requests.Request`, requires; this project otherwise uses `httpx`, but `google-auth`'s official verification path is built around `requests`, and using the library's own documented transport mattered more here than staying consistent with `httpx`) — `google.oauth2.id_token.verify_oauth2_token()` validates the signature against Google's published public keys, issuer, and expiry; `email_verified`/`email` presence are checked manually afterward.

   **Account-linking logic (`GoogleSignInView.post()`, kept in the view rather than the serializer — deliberately, see the comment on `GoogleSignInSerializer` itself: this endpoint is fundamentally a login action with an optional account-creation side effect, closer to how `LoginView` already does all its own branching directly rather than delegating to a serializer, than to a `ModelSerializer.create()` case):**

That's a correct assumption *only* if the screen is always entered immediately after accepting a fresh alert (status `dispatched`, nothing pressed yet) and never left before completion — true for the original flow, false the moment this fix makes the screen reachable for an incident that's already `on_the_way`/`arrived_on_scene`. The screen also gained the same defensive "redirect to dashboard if the incident turns out to already be `completed`/`cancelled`" check `emergency-active.tsx` already had — belt-and-suspenders, since the history screen's own resolved/non-terminal branch should prevent this case from being reached that way, but the incident's status can also change server-side (completed by someone else, timing) between the list being fetched and the tap landing.

   **One more fix, adjacent but directly relevant to this exact stuck-incident scenario:** `emergency-active.tsx`'s cancel handler used to call the try/catch around the cancel API request but then unconditionally `router.replace()` to the dashboard *outside* the try/catch — meaning a failed cancel (e.g. exactly this case: status already past `ACTIVE`, backend correctly rejects it) silently navigated the patient away as if cancellation had succeeded, with the incident still genuinely live behind them. Left as-is, this would have actively undermined the whole point of making the screen reachable again: a patient reaching a stuck `on_the_way` incident through the new tap-through, tapping the always-visible "Cancel Emergency" button, and being misled into thinking it worked. Fixed to only navigate away on a successful cancel, and to show `Alert.alert('Could Not Cancel', ...)` on failure instead of silently leaving.

   **Cancellation window widened — product decision, added in a further follow-up.** Cancellation used to be blocked the instant an ambulance was dispatched (`cancellable = {PENDING_CONFIRMATION, ACTIVE}` in `cancel_incident()`, `emergencies/services.py`) — this was the actual rule in effect during the stuck-incident scenario documented above, and part of why that patient had no recourse. Product decision: a patient can now cancel through and including `ON_THE_WAY`, but not once `ARRIVED_ON_SCENE` or later — reasoning being that before the crew is physically on scene, cancelling still saves resources on a false alarm, but once they're there, only the crew on scene can assess and resolve the situation, not the patient unilaterally. `cancellable` is now `{PENDING_CONFIRMATION, ACTIVE, DISPATCHED, ON_THE_WAY}`. Covered by `emergencies/tests.py::SOSCancelTest` (`test_cancel_dispatched_incident`, `test_cancel_on_the_way_incident`, `test_cannot_cancel_arrived_on_scene_incident` — the existing `test_cannot_cancel_completed_incident` already covered the terminal-status side).

   **Keeping the ambulance side correctly informed, now that cancellation can happen post-dispatch — investigated before implementing, not assumed.** Before this change, cancellation and "an ambulance is assigned" were mutually exclusive states (dispatch requires `ACTIVE`→`DISPATCHED`, and cancellation was only ever legal pre-dispatch), so an assigned ambulance/EMT learning that "their" patient cancelled was never a real code path — it simply couldn't happen. It's a real path now, so this was checked point by point rather than assumed fine:
   - **`active-response.tsx` already handles this correctly, and already anticipated it.** Its 12s `update_location` PATCH loop reads `status` back from every response (`IncidentAmbulanceActiveSerializer` includes it) and already treats `completed`/`cancelled` as "stop the interval, alert the EMT, navigate to dashboard" — this was built during the SC-15 live-location work specifically to cover "patient cancelled while I was still en route" (see that section above), a case that, before today, could never actually trigger. It does now, and the existing handling is correct as-is — no changes needed there.
   - **`_get_assigned_incident()`** (the ownership lookup shared by `update_location`/`update_status`/`select_hospital`/`treatment_notes`) only checks `ambulance_service == effective_ambulance_service`, not `medical_profile_access_granted` or incident status — so none of those endpoints start 404ing for the assigned ambulance just because the incident got cancelled. The EMT can still submit treatment notes, etc. for a cancelled incident's record if needed; nothing about cancellation locks them out of the incident itself.
   - **`medical_detail`** (`IsAcceptingAmbulance`) *does* check `medical_profile_access_granted`, which `Incident.update_status()` already correctly flips to `False` on cancellation (NFR-04 — the same flip completion already triggered; cancellation was just never reachable post-grant before now). This only matters if something calls `medical_detail` again after cancellation — `active-response.tsx` only calls it once, on initial mount, so this doesn't disrupt an open session; it just correctly closes off access to the medical profile going forward, same as completion already does.
   - **`my_responses`/`ambulance-history.tsx`** has no status filter — it already lists a cancelled incident correctly, right alongside completed/other in-progress ones, with no separate handling needed (this predates today's change, from the manual-fallback fix above).
   - **`my_active`** correctly stops returning a cancelled incident (it's in the terminal-status exclude list), so a later relaunch/session-restore won't route the EMT back into a dead incident.
   - **`active_alerts`** (the pre-accept broadcast queue) is unaffected either way — it only ever lists unassigned `ACTIVE` incidents, and this change only concerns incidents that already have an ambulance assigned.
   - Added a `_notify(...)` stub call in `cancel_incident()` (guarded on `incident.ambulance_service_id` being set, so pre-dispatch cancellations — which have no ambulance to notify — don't call it) — matching the same logger-stub convention every other state-transition point in `services.py` already follows (`accept_incident` notifies the patient, `select_destination_hospital` notifies the hospital). This is a log-line stub, not a real push notification (this project has none — see the module docstring), and isn't what actually keeps the EMT's live screen informed; the `update_location` response is.
   - **One pre-existing edge case, not a regression from this change:** if the EMT never grants location permission, `active-response.tsx`'s `sendLocationTick()` returns before calling `update_location` at all, so that particular EMT wouldn't learn of a cancellation from this loop specifically. Not addressed here — the same permission denial already breaks the screen's core live-location/map functionality regardless of cancellation, and `my_active` still correctly stops re-routing them to a cancelled incident on their next app launch either way.

   **Mobile: `emergency-active.tsx`'s Cancel button now hides once cancellation is no longer possible, instead of staying visible only to fail.** Previously the button was unconditional — always rendered regardless of status — relying entirely on the backend rejecting the request (with the "Could Not Cancel" alert added in the fix above) once past `ACTIVE`. Matching this codebase's established "prevent the action, don't just error after the fact" pattern (see `register.tsx`'s consent checkbox), the button is now gated on a `canCancel` check that mirrors the backend's cancellable set exactly (`pending_confirmation`/`active`/`dispatched`/`on_the_way`; defaults to cancellable while `incident` is still `null`/loading). Once `arrived_on_scene` or later, the button is replaced with a plain informational notice ("The crew is on scene — cancellation is no longer available...") instead of disappearing with no explanation. The backend remains the real enforcement point regardless — this is UX, not the security boundary.

**Location is now REQUIRED on every SOS trigger path — new (both the in-app patient SOS and the public NFC page).** Investigation first: before this, neither path guaranteed a location. Mobile only requested permission inside `triggerSOS()` (after the hold finished), silently triggered with `null` coordinates if permission was denied, threw into a generic "SOS Failed" alert if location services were off, and had no timeout on `getCurrentPositionAsync` (could hang on "SENDING..."). The NFC page never asked the browser for geolocation at all and POSTed a `null` body. A location-less incident can't be dispatched to, so all of that is replaced with "no location, no incident":

  - **Backend:** `SOSTriggerSerializer` and the new `NFCTriggerSerializer` share `_RequiredLocationFields` — `latitude`/`longitude` required (range-checked ±90/±180; `location_accuracy_metres` optional), 400 with a clear message if missing/null/out of range. `services.trigger_nfc_sos(tag, location)` now takes the validated coordinates; `NFCTagTriggerView` validates AFTER the tag lookup (unknown token stays 404) and BEFORE the service (no incident without coordinates). For the NFC path these are the **bystander's** device coordinates, used as a proxy for the patient's position. `services.trigger_sos()` itself is deliberately still permissive (the requirement is enforced at the request boundary; many tests call the service directly).
  - **Mobile:** `utils/get-sos-location.ts` (`expo-location` injected so it's testable in plain Node): permission (already granted / ask) -> fresh fix capped at 6s -> `getLastKnownPositionAsync` (max age 10 min) -> else a categorised failure (`permission_denied` / `unavailable`). `patient-dashboard.tsx` requests permission on dashboard load (non-blocking, silent on denial) and `triggerSOS()` refuses to create an incident without a location: it shows a calm modal ("We need your location to send help", how to enable it, **Try again** / **Open Settings** / Not now) instead of the old generic alert. `emergency-active.tsx`'s "📍 Your location has been shared" line now renders only when the incident has coordinates.
  - **Web NFC page:** `utils/geolocation.js` wraps `navigator.geolocation.getCurrentPosition` (8s timeout, categorised `denied`/`unavailable`/`timeout`, never rejects). `NFCTrigger.jsx` requests location once the tag is known to be `paired` (not for invalid/unpaired/already-alerted tags), shows "Getting your location…", and only shows the hold-to-confirm button once it has a fix — the coordinates go in the POST body. Denied/unavailable/timeout shows the same calm blocking message with a Try again button and NO emergency button. Caveat: per the Geolocation spec the browser timeout doesn't start until the user answers the permission prompt, so an ignored prompt stays on "Getting your location…". Browsers also require HTTPS for geolocation (the deployed web app must be served over it).
  - **Downstream "no location" handling is now unreachable for NEW incidents but deliberately left in place** (SMS "Location unavailable.", the map's "Waiting for your location…" placeholder, the route endpoint's `available: false`): they still serve incidents created before this change and any direct service-level `trigger_sos()` call, and removing them isn't needed for correctness. The offline-queue endpoint (dead `tasks` import, `was_offline_queued` never sent) was out of scope and is tracked separately.
  - **Tests:** backend `SOSTriggerLocationRequiredHTTPTest` (missing/partial/null/out-of-range rejected with nothing created, valid coordinates + accuracy stored), NFC trigger tests updated to send coordinates plus new ones (missing/partial/out-of-range rejected, unknown token still 404 without a body, bystander coordinates stored and reach the contact SMS). Frontend logic tests run with Node's built-in runner, no new dependencies: web `npm test` (`utils/geolocation.test.js`, 8 tests — success/rounding, denied, unavailable, timeout, no API, sync throw, options, single callback) and mobile `npm test` (`utils/get-sos-location.test.mjs`, 9 tests — granted, prompt-then-allow, denied blocks with no location calls, services-off, timeout -> last-known, timeout with no fallback never hangs, provider error -> last-known, last-known throwing, permission check throwing). The React components' blocked/retry rendering itself is verified by build/type-check only — there is no component-test setup (RN Testing Library / Vitest) in either frontend.

**NFC tag admin fixes — copy, patient picker, unpair, void (new).** All in `mera-admin/NFCTags.jsx` + `emergencies/`.
  - **Copy buttons.** The old handler was `navigator.clipboard?.writeText(text).catch(() => {})` — silently a no-op whenever `navigator.clipboard` is undefined (any non-HTTPS origin, e.g. a LAN dev URL) or `writeText` rejects. New `utils/clipboard.js::copyText()` tries the Clipboard API, then falls back to a hidden textarea + `execCommand('copy')`, and returns a boolean; the shared `components/CopyButton.jsx` shows "Copied!" / "Copy failed" instead of silence. Used per-row and "Copy all" on the batch-generation screen, and as a new **Tag URL** column (Copy URL + Open) in the tag list. Unit-tested (`npm test`, includes the insecure-context case).
  - **Patient picker bug.** Root cause (from reading the code — not reproduced in a browser): the picker was a native `<select size={n}>` controlled by `selectedPatientId` (initially `''`). When search narrowed to ONE result, `size=1` renders a dropdown that *displays* its only option as selected while React state is still `''`; clicking an already-displayed option fires no `change`, so state never updated and Pair's validation rejected it. Replaced with a click-to-select list whose rows set `selectedPatient` (the whole object, not an index into a list that changes as you type); the checkbox/highlight are rendered from that same state and Pair validates that same state; a "Selected: …" chip keeps the choice visible even if further searching drops it from the results. Modal widened (680px, 300px list).
  - **Unpair** — `POST /nfc-tags/{id}/unpair/`: clears `patient`/`paired_at`; token and short code stay valid so the sticker can be re-paired to someone else. Rejects an unpaired or voided tag.
  - **Void** — `POST /nfc-tags/{id}/void/`: **soft void, not a hard delete** (built deliberately, mirroring the account deactivate pattern). `NFCTag.voided_at` (migration `0005`) is set once and never cleared: the public status endpoint reports a voided token as `"invalid"` (indistinguishable from an unknown one), the public trigger 404s, and pair/unpair/void reject it. The row is kept as an audit trail and so the token/short code stay reserved and can never be regenerated; `patient` is left intact to show whose sticker it was. **Deliberately irreversible** — a compromised token must not come back; there's no restore action. List responses now carry `status` (`paired`/`unpaired`/`voided`) and `voided_at`; `?paired=true|false` covers live tags only and `?voided=true` lists voided ones. UI: Unpair/Void row buttons with confirm dialogs, a Voided filter tab, voided rows dimmed with copy/open disabled.
  - **Tests:** backend `NFCTagUnpairAndVoidTest` (10 tests); web `clipboard.test.js` (5).
