# MERA — Project Context for AI Assistants

Paste this whole document into a new conversation with Claude, ChatGPT, or any AI assistant before asking for help on this project. It gives the assistant the context it needs to give suggestions that actually fit our architecture instead of generic advice.

---

## What MERA is

MERA (Medical Emergency Response Application) is a South African medical emergency platform connecting **patients**, **hospitals**, and **ambulance services**. It's a year-long capstone project for a team called NonaCrest, with formal SRS and UI specification documents behind it. It must comply with South Africa's POPI Act (data protection law).

## Repo structure

Single repo, three top-level folders:

```
MERA-APP-Nonacrest/
├── backend/           Django REST Framework API (single backend, shared by both frontends)
├── mobile-frontend/   React Native / Expo app — for Patients and EMTs
└── web-frontend/      React + Vite app — for Hospital Admins, Ambulance Admins, and MERA super-admins
```

**One backend serves both frontends.** Nothing is duplicated. Any new endpoint should be built once in `backend/` and consumed by whichever frontend(s) need it.

## User roles (this is the most important part to get right)

There are **five roles**, and each has a specific home:

| Role | Where they log in | What they do |
|---|---|---|
| **Patient** | Mobile app | Self-registers. Triggers SOS, manages own medical profile, uses AI chatbot. |
| **EMT** | Mobile app | Does **not** self-register. Their account is created by their Ambulance Admin. Responds to SOS alerts, updates incident status, submits treatment notes. |
| **Hospital Admin** | Web app | Does **not** self-register. Account created by MERA super-admin during institutional onboarding. Manages patient verification queue, sees incoming ambulance notifications. |
| **Ambulance Admin** | Web app | Does **not** self-register. Account created by MERA super-admin. Creates/manages EMT accounts under their service. |
| **MERA super-admin** | Web app | Internal MERA team only. Onboards new hospital/ambulance institutions, creates their admin accounts, manages/deletes any account platform-wide, views platform stats. |

**Key principle: only Patients self-register.** Every other role's account is created by someone above them in the hierarchy (MERA admin → Hospital/Ambulance admin → EMT). This replaced an earlier design where hospitals and ambulances self-registered with a multi-step approval flow — that flow is being phased out in favor of top-down account creation.

**Important, still evolving:** Hospitals and hospital-related screens are being **removed from the mobile app entirely** and moved fully to the web app. The mobile app will end up serving only Patients and EMTs.

**Role naming — current transitional state (read this carefully before touching `accounts/models.py`):**

The `Role` enum on `User` currently has **seven** values, not five, because the new roles were added *alongside* the old ones rather than replacing them yet:

```
patient            — unchanged, still used
hospital           — OLD name for what is becoming hospital_admin. Still referenced
                      throughout permissions.py, views.py, verification app, etc.
ambulance_service  — OLD name for what is becoming ambulance_admin. Same situation.
hospital_admin     — NEW. Not yet wired into permissions/views beyond the model choice
                      and the web login page's role check.
ambulance_admin     — NEW. Same as above. This is an institution-level account
                      (the ambulance service itself), NOT an individual EMT.
emt                — NEW. Individual crew member, mobile-only, does not self-register.
                      Belongs to exactly one ambulance_admin (see field below).
mera_admin          — NEW. Platform-wide super-admin, web-only.
```

**This is a deliberate, temporary state.** The team has not yet decided whether to do a hard rename (`hospital` → `hospital_admin`, `ambulance_service` → `ambulance_admin`) across every file that references the old names, or to migrate references gradually. **Update:** old and new role names are now treated as equivalent everywhere permission/role checks happen. `accounts/models.py` defines `HOSPITAL_ROLES = {Role.HOSPITAL, Role.HOSPITAL_ADMIN}` and `AMBULANCE_ROLES = {Role.AMBULANCE_SERVICE, Role.AMBULANCE_ADMIN}`, and `IsHospital`, `IsAmbulanceService`, `HospitalListView`, and other role filters across `accounts/`, `verification/`, and `emergencies/` all check membership in these sets (`role__in=HOSPITAL_ROLES`, etc.) rather than a single literal role string. Accounts created with either the old or new role name are treated identically by these checks. The underlying rename decision (collapsing to one canonical name per role) is still not made — these sets are the interim bridge — but the practical blocker (new-role accounts failing old-name-only checks) described in earlier versions of this doc has been resolved.

**EMT ↔ Ambulance Admin link:** Each EMT belongs to exactly one ambulance service. This is modeled as a self-referencing `ForeignKey` on `User`:

```python
ambulance_service = models.ForeignKey(
    "self", null=True, blank=True, on_delete=models.SET_NULL,
    related_name="emts", limit_choices_to={"role": "ambulance_admin"},
)
```

An `ambulance_admin` user's EMTs are accessible via `ambulance_admin_user.emts.all()`.

**Account creation hierarchy (planned, not yet built):**
- MERA admin creates hospital_admin accounts and ambulance_admin accounts (institution onboarding)
- Ambulance admin creates EMT accounts (EMTs never self-register)
- Nobody creates MERA admin accounts through the app — these are set up directly (e.g. via Django shell) since it's the internal MERA team only

**Web login page:** Built at `web-frontend/src/pages/auth/Login.jsx`. Users select their role (MERA Admin / Hospital Admin / Ambulance Admin) via tabs *before* entering credentials. The frontend compares the selected role against `response.user.role` from the login API and **rejects login client-side if they don't match**, even though the backend would otherwise authenticate successfully. This is a deliberate UX choice, not a security boundary — real authorization still happens via backend permission classes on each endpoint.

## Tech stack

- **Backend:** Django REST Framework, PostgreSQL, JWT auth (`djangorestframework-simplejwt`)
- **Mobile frontend:** React Native + Expo (TypeScript)
- **Web frontend:** React + Vite (JavaScript), `react-router-dom` for routing, `recharts` for charts, `lucide-react` for icons. Folder structure under `src/pages/` is split by role (`auth/`, `hospital-admin/`, `ambulance-admin/`, `mera-admin/`) so each teammate can work in their own lane. Only `auth/Login.jsx` exists so far — the other three folders are still empty placeholders (`.gitkeep` only).
- **AI chatbot:** Server-side only, calls the Anthropic API from Django (never from either frontend — API keys must never touch client code)
- **Hosting:** Backend deployed on Render (free tier). Database also on Render Postgres (free tier — **expires and must be recreated roughly every 30 days**, so don't assume data persists indefinitely on the dev database).

## Backend app structure (Django apps)

- `accounts` — custom `User` model with a `role` field. Currently holds both old (`hospital`, `ambulance_service`) and new (`hospital_admin`, `ambulance_admin`, `emt`, `mera_admin`) role values simultaneously — see the "Role naming" section above before changing anything here. Endpoint additions:
  - Ambulance admin — EMT management: `PATCH /auth/admin/emts/{id}/` (edit `full_name`/`phone_number`/`email` on your own EMT — role and password are not editable here) and `DELETE /auth/admin/emts/{id}/` (soft-deactivate: sets `is_active=False`, does **not** hard-delete — same pattern as institutional approval/rejection, chosen because it's the only removal pattern already in this codebase and it preserves incident/treatment-note history). Both `IsAmbulanceService`-gated and scoped to EMTs where `ambulance_service == request.user`; an EMT belonging to a different ambulance service returns 404 (not 403) so ownership isn't leaked, matching `verification`/`medical_profiles`'s existing lookup pattern.
  - MERA admin — institutions/stats/accounts (`IsMERAAdmin`-gated): `GET /auth/admin/institutions/` (hospital_admin + ambulance_admin accounts, both old/new role names via `HOSPITAL_ROLES`/`AMBULANCE_ROLES`; `InstitutionSummarySerializer` now also returns `is_active` — it didn't before, only `institutional_status`, a different field, which meant the frontend had no way to tell a deactivated institution from an active one) and `GET /auth/admin/users/` (every account, any role) both accept `?search=` — case-insensitive partial match, OR'd across whichever name field the row actually has populated (`full_name`/`facility_name`/`service_name`) plus `email`; safe to apply the same combined filter regardless of role since an irrelevant field is just blank and never matches. `GET /auth/admin/users/` also now orders `-is_active` first (active accounts before deactivated ones), then `-date_joined` as the tiebreaker within each group — it used to be pure `-date_joined`. `GET /auth/admin/stats/` (counts: patients, hospitals, ambulance services, EMTs, `emergencies.Incident` total) — the four role-based counts now filter `is_active=True`; previously they counted every account ever created regardless of status, so e.g. deactivating an ambulance_admin's EMTs never moved the dashboard number at all. `total_incidents` is unaffected — an `Incident` has no active/inactive concept. Covered by `accounts/tests.py::MERAAdminInstitutionsStatsUsersTest::test_stats_only_counts_active_accounts` (the pre-existing `test_stats` alone couldn't prove this, since its fixtures are all active by default — it would've passed identically with or without the filter). `PATCH /auth/admin/users/{id}/` — new: MERA admin edits any account's basic info (`full_name`/`email`/`phone_number`/`facility_name`/`service_name`); role and password are deliberately not editable here (role is permanent, password changes go through the reset flow) — see `AdminUserEditSerializer`. `PATCH /auth/admin/users/{id}/deactivate/` (sets `is_active=False` on any account regardless of role; a MERA admin can still deactivate another mera_admin's account, but is blocked with 400 from deactivating their *own* account, to prevent accidental self-lockout) **now cascades**: deactivating an ambulance_admin (or legacy ambulance_service) also deactivates every currently-active EMT linked to it via `.emts` — an EMT under a shut-down service shouldn't be able to keep responding to incidents. Hospital admins have no subordinate accounts, so nothing cascades for them. Response now includes `deactivated_emt_count`. `PATCH /auth/admin/users/{id}/reactivate/` — new: `ReactivateUserView`, the inverse. No role restriction (mirrors deactivate) and deliberately no self-lockout-style guard — `djangorestframework-simplejwt`'s `JWTAuthentication.get_user()` already re-checks `is_active` against the DB on *every* authenticated request, not just at login, so a deactivated account's own token already stops working before its next request goes through; a MERA admin cannot be authenticated while their own account is inactive, so "reactivate yourself" can't arise through the API at all. Also cascades the same way deactivate does — reactivating an ambulance_admin reactivates every currently-inactive EMT linked to it too (`reactivated_emt_count` in the response), otherwise cascading deactivation would be a one-way trip requiring the admin to manually reactivate each EMT individually afterward. No "already active" guard either, matching deactivate's own lack of an "already inactive" guard — both directions are idempotent successes, not errors.

**Institution reassignment (`successor_of`) — new.** `HospitalAdminCreationSerializer`/`AmbulanceAdminCreationSerializer` (i.e. `POST /auth/admin/create/hospital-admin/` and `.../create/ambulance-admin/`) now accept an optional `successor_of` field: the id of an existing **deactivated** account of the *same* institution type. Used when a hospital/ambulance's admin account was deactivated (e.g. staff turnover) and MERA is onboarding a replacement admin for the same physical institution, rather than starting from a blank slate. Validation (`_validate_successor` in `accounts/serializers.py`) rejects — with a clear `successor_of` field error, not a generic 400 — a target that doesn't exist, isn't deactivated, or is the wrong role type (e.g. pointing an ambulance creation at a deactivated hospital). When valid: `HOSPITAL_IDENTITY_FIELDS`/`AMBULANCE_IDENTITY_FIELDS` (facility/service identity — name, type, address, dispatch info, etc.) are copied from the old account onto the new one, **overriding** whatever those specific fields were set to in the request body — continuity of the institution's identity is the point, so the old account wins. The new admin's own `email`/`password`/`admin_contact_name`/`admin_phone` are never touched by this — those are the incoming person's, not inherited. For ambulance reassignment specifically, every EMT still pointing at the old account's `ambulance_service` FK is re-linked to the new account **and reactivated** in the same `.update()` call (regardless of their prior `is_active` state) — that's the actual intent of reassignment ("this new admin can use these EMTs again"), not a two-step process where re-linking happens now and someone has to remember to reactivate each EMT separately later. (`ReactivateUserView`, documented above, is the standalone version of this same reasoning — independently useful for reactivating a single account without a full reassignment.) The old account itself is left exactly as-is: still deactivated, still in the database, still the correct attribution on every historical `Incident`/`VerificationRequest` that already pointed at it — nothing about this flow touches those records, only the *current* EMT-linkage and institution-identity fields on the User rows change. Hospitals have no subordinate accounts, so hospital reassignment is just the identity-field copy, no re-linking step. Covered by `accounts/tests.py::InstitutionReassignmentTest`.

**Shared row-actions menu (web frontend) — new.** `web-frontend/src/components/UserRowActions.jsx` is a single component (a "⋮" menu — Edit / Deactivate / Reactivate, whichever applies — plus the Edit modal) used by both `pages/mera-admin/Users.jsx` and `pages/mera-admin/Institutions.jsx`. Both pages act on the exact same accounts via the exact same `PATCH /auth/admin/users/{id}/[deactivate|reactivate|]` endpoints, just surfaced from two different list views, so the component owns the whole interaction itself — menu open/close, the deactivate confirm + EMT-cascade-count alert, busy/error state, the edit modal — rather than each page reimplementing it. A page just renders `<UserRowActions user={row} onChanged={patch => ...} />` per row and merges whatever `onChanged` is called with into its own list state; `UserRowActions` reads `useAuth()` internally to work out `isSelf` on its own; it doesn't need to be told. Building this is what surfaced the `InstitutionSummarySerializer` gap noted above — without `is_active` in that response, every institution row would have shown "Deactivate" and never "Reactivate", regardless of its real state.

A related bug shipped in that same batch of work, caught and fixed the next session: `Institutions.jsx`'s Status column was still rendering `institutional_status` (approved/pending/rejected — a separate field from `is_active`, and one that's currently hardcoded to `"approved"` for every account in this prototype; see bypass #1 below) instead of `is_active`. Deactivate/reactivate only ever write `is_active`, never `institutional_status`, so the badge silently never moved — an admin could deactivate an institution from that page and it would keep reading "Approved" forever, even though `is_active` (and the account's actual ability to log in) had genuinely changed; `Users.jsx` showed the correct state the whole time since it was already reading `is_active`. Fixed by switching that column to `is_active`-based active/inactive, same as `Users.jsx`. Deliberately did **not** add `institutional_status` as a second column — it can't currently vary (every real account in this prototype is created with it hardcoded to `approved`), so a second column would just repeat an identical badge on every row; worth revisiting once the approval-gate bypass is reinstated and `institutional_status` becomes meaningful again. Verified against the real API, not just by reading the code: `is_active` was confirmed to flip `true → false → true` in `GET /auth/admin/institutions/`'s response across a real deactivate/reactivate cycle, while `institutional_status` stayed `"approved"` throughout.

**Login now actually checks `is_active` — a real gap, not one of the documented prototype bypasses below.** `accounts/views.py`, `LoginView` never checked `is_active` at all, for any role — this is separate from bypass #1 in the "Prototype safety bypasses" section, which is specifically about the *pending/rejected institutional-status* messaging block (still commented out, untouched). Nothing else covered plain deactivation either, so a deactivated account of any role could log in and receive a fully valid token. In practice this was less severe than it sounds: `djangorestframework-simplejwt`'s `JWTAuthentication.get_user()` already re-checks `is_active` on every *subsequent* authenticated request, so that token would fail on its very next real use regardless — but login itself still had no business returning 200 with real tokens for a deactivated account. Fixed: `LoginView` now returns 403 (`"This account has been deactivated. Contact your administrator."`) for `is_active=False`, checked before the still-bypassed institutional-status block. This fix was a precondition for the new reactivate endpoint to mean anything — "deactivate" needs to actually block access for "reactivate" to actually restore it. Side effect worth knowing about: `accounts/tests.py::LoginTest::test_pending_institutional_account_blocked` now passes — not because bypass #1 was re-enabled, but because that test's fixture also happens to set `is_active=False`, which this new, separate check now catches. The known-failure count dropped from 4 to 3 as a result; see "Known test suite gaps" below.
- `medical_profiles` — patient medical data, includes a `data_sharing_consent` field (for hospital/ambulance access) that is **separate** from `ai_chatbot_consent` (for AI chatbot use) — these must never be conflated. Also has the hospital **Patient List** endpoint (SC-13): `GET /medical-profile/patients/`, `IsHospital`-gated, returns every patient tied to the requesting hospital across *all* verification statuses (not just one queue bucket), with optional `?search=` (patient name, case-insensitive) and `?status=verified|pending|flagged|info_requested` filters. It determines "belongs to this hospital" the same way the `verification` app's queue/approved/flagged endpoints do — via `VerificationRequest.objects.filter(hospital=request.user)` — since `MedicalProfile` itself has no hospital field. This means `medical_profiles` now imports `VerificationRequest` from `verification`, on top of the existing `verification` → `medical_profiles` dependency, so the two apps are mutually coupled. **Deliberate design decision:** a patient stays visible in a hospital's roster based on *any past* `VerificationRequest` to that hospital, even after the patient later moves to a different hospital for current care — this is intentional, not an oversight. The product reasoning is that patients may want their medical history visible to every hospital that has ever treated them, not just their current one. Do not "fix" this by restricting the roster to the patient's most recent hospital without raising it as a product discussion first.
- `emergencies` — incident/SOS lifecycle. **EMTs can now respond to incidents.** Previously, `emt` was missing from every ambulance-side permission check on `IncidentViewSet` (`active_alerts`, `accept`, `select_hospital`, `update_status`, `treatment_notes`, `my_responses`, plus `get_queryset()` and `IsAcceptingAmbulance`), so EMTs got 403s trying to view or act on incidents despite that being their whole job on mobile. Fixed by adding `emergencies/permissions.py::AMBULANCE_RESPONDER_ROLES = AMBULANCE_ROLES | {Role.EMT}` and a new `IsAmbulanceResponder` permission class, used in place of `accounts.permissions.IsAmbulanceService` on those six actions and in `get_queryset()`. Deliberately did **not** add `emt` to `AMBULANCE_ROLES` itself or to `IsAmbulanceService` — that class also gates EMT-*management* endpoints (`EMTCreateView`, `MyEMTsListView`, `EMTUpdateView`) and `AvailabilityToggleView`, which must stay institution-account-only (an EMT must not manage other EMTs or toggle the whole service's dispatch availability). `active_alerts`' broadcast query was already unfiltered by ambulance service (global list of unassigned ACTIVE incidents) — same behavior now applies to EMTs unchanged, no new filtering logic was added.

**Live location tracking + routing (maps feature) — new.** Backend groundwork for the "real maps during an active incident" roadmap item (see priority 6 below) — no frontend map wiring yet, just the data plumbing. `Incident` gained `ambulance_lat`/`ambulance_lng` (`FloatField`, nullable) — deliberately `FloatField` rather than the `DecimalField` used for the patient's one-time SOS `latitude`/`longitude` above, since this is a live value overwritten repeatedly while en route, not a fixed record. Three pieces:
  - `PATCH /incidents/{id}/update_location/` — the assigned EMT/ambulance reports their own current GPS position. `IsAmbulanceResponder`-gated, ownership-scoped via the same `_get_assigned_incident()` helper `select_hospital`/`update_status`/`treatment_notes` already use (resolves through `effective_ambulance_service`, so any EMT on the assigned crew can send pings, not just whoever accepted; a mismatched ambulance gets 404, not 403, matching that helper's existing not-yours-vs-doesn't-exist behavior). Deliberately **not** written to `EmergencyLog` — that log is for meaningful state transitions, and a GPS ping arriving every few seconds would spam it; `incident.updated_at` still moves on every call.
  - `GET /incidents/{id}/` (the patient app's existing SC-06 tracking-screen poll, `mobile-frontend/app/(patient)/emergency-active.tsx`, `ENDPOINTS.getIncident`, polled every 10s) now includes `ambulance_lat`/`ambulance_lng` in its response — `null` until the ambulance's first `update_location` call. `IncidentAmbulanceActiveSerializer` (returned by `update_location` itself, `medical_detail`, `accept`, etc.) also carries both fields now, so the ambulance side sees back what it just saved.
  - `GET /incidents/{id}/route/` — server-side call to Google's Routes API (`computeRoutes`), origin = current ambulance position, destination = patient's SOS location. New `IsIncidentPatientOrAssignedAmbulance` permission (`emergencies/permissions.py`) grants access to the incident's own patient OR its assigned ambulance/EMT — checked as an object permission via `self.check_object_permissions(...)` after `_get_incident_object(pk)`, the same pattern `medical_detail` already uses for `IsAcceptingAmbulance`. Unlike `IsAcceptingAmbulance`, this does **not** require `medical_profile_access_granted` — tracking data isn't medical data, so it stays reachable even if that flag isn't set. If either `ambulance_lat`/`lng` or the patient's `latitude`/`longitude` isn't populated yet, the endpoint returns `200 {"available": false, "detail": "..."}` rather than erroring — this is the expected steady-state response before the ambulance's first location ping, so a polling client shouldn't have to treat it as a failure. A Google API failure (network error, non-2xx, missing key) is caught broadly in the view (mirrors `chatbot/views.py`'s handling of Anthropic failures) and returns `503`, never a 500.

  **The Google Maps API key is backend-only, mirroring the existing `ANTHROPIC_API_KEY` pattern exactly** — read from `GOOGLE_MAPS_API_KEY` (`settings.py`, right next to `ANTHROPIC_API_KEY`), used only inside `emergencies/services.py::get_route()`, sent to Google exclusively via the `X-Goog-Api-Key` request *header* (never in the request body/URL, never echoed back in the response), and never present in any response either frontend receives. The same "secrets never go in Git" rule applies — add it to your local `.env`, never commit it.

  **Pricing-tier care:** `get_route()`'s `X-Goog-FieldMask` header requests only `routes.duration`, `routes.distanceMeters`, and `routes.polyline.encodedPolyline` — Google's **Basic** tier. Adding traffic-aware fields (e.g. `routeTravelAdvisory`) or advanced routing options bumps a call into the pricier **Advanced** tier — don't add response fields to that mask without checking which tier they fall under first.

  **Testing the Google call without spending real quota:** tests never hit the network. `emergencies.services.httpx.post` (the one line that actually calls Google) is mocked directly via `unittest.mock.patch`, returning a bare `Mock()` shaped like just the two things `get_route()` touches on an `httpx.Response` — `.raise_for_status()` (no-op) and `.json()` (returns a fake `computeRoutes` payload). `GOOGLE_MAPS_API_KEY` is supplied per-test via `@override_settings(...)` since the real dev `.env` may not have it set. Covered by `emergencies/tests.py::UpdateLocationTest` (6 tests — success, ownership rejection for an unassigned ambulance and for a patient, validation), `PatientStatusIncludesAmbulanceLocationTest` (confirms `ambulance_lat`/`lng` are `null` then populated across a real `update_location` → `GET /incidents/{id}/` round trip), and `RouteEndpointTest` (10 tests — success for both patient and assigned ambulance/EMT, access denied for an unrelated patient/ambulance, the API key never leaking into the request body or response, missing-ambulance-location and missing-patient-location both handled without a crash, a mocked Google failure and a missing-API-key case both degrading to `503` instead of `500`).

  **Patient-side map — done.** `mobile-frontend/app/(patient)/emergency-active.tsx` (SC-06) now renders a real `react-native-maps` `MapView` instead of the hardcoded `PATIENT_LOCATION`/`AMBULANCE_LOCATION` placeholder constants (both deleted). `react-native-maps@1.20.1` was already an installed dependency (`package.json`) and needs **no additional Expo config** to work in Expo Go — it's one of the packages Expo Go ships pre-bundled native support for, and this project's dev workflow is plain `expo start`/Expo Go (no `eas.json`, no dev-client), so config-plugin entries in `app.json` (which only take effect on `expo prebuild`/EAS/dev-client builds) wouldn't even be read by Expo Go anyway. Two data-shape details that matter here and are easy to get backwards: `incident.latitude`/`longitude` are Django `DecimalField`s, which DRF serializes as **strings** (e.g. `"-26.204100"`) by default — `parseFloat()` before handing them to a `Marker`, same as the existing `parseFloat()` calls already in `(ambulance)/dashboard.tsx`. `ambulance_lat`/`ambulance_lng` are plain `FloatField`s and arrive as real JSON numbers — no parsing needed, and parsing an already-numeric value would silently still work but is pointless. Both coordinates are nullable (a SOS can be triggered without GPS; the ambulance has none until its first `update_location` call), so both resolve to `null` rather than `NaN`: no patient coordinate → the map itself is replaced with a "Waiting for your location…" placeholder view (same size/rounded-corner styling as the map, so nothing jumps in the layout when it later appears); no ambulance coordinate → the map renders with just the patient's marker, no ambulance marker, no polyline, no crash. The existing dispatch card/status-checklist/cancel-button UI is untouched — the map is inserted between them, same position as the original hardcoded one.

  **Real route polyline (patient side) — done, added in a follow-up pass.** The straight-line placeholder between the two markers is gone — `emergency-active.tsx` now calls `GET /incidents/{id}/route/` and decodes the real polyline via the same `decodePolyline()` used on the EMT side (`mobile-frontend/utils/decode-polyline.ts` — reused, not duplicated). Throttling reuses `active-response.tsx`'s exact distance/time-gate reasoning and constants (150m movement + 30s floor + 60s ceiling — see "Route-call throttling — reasoning" above), just measuring a different party's movement: the EMT side gates on the EMT's own device GPS changing between their 12s ticks, since that's the thing moving from their perspective; the patient side gates on the **ambulance's server-reported position** changing between the patient's own 10s incident polls, since the patient's own SOS location never moves — only the ambulance's does, from the patient's point of view. The route call itself is folded into the existing `fetchIncident` poll (called right after `setIncident(data)`, using that same response's freshly-polled `ambulance_lat`/`lng` as the "current position" for the distance check) rather than a second independent interval — the incident poll already runs every 10s and already carries the ambulance's latest position for free, so no additional polling loop is needed just to know when to check. Same graceful degradation as the EMT side: route unavailable or the call fails → no line drawn (not even a straight-line fallback) → both markers still render, no crash. This resolves the asymmetry noted in the EMT-side write-up below — both screens now render the real route, not just one.

  **Smooth ambulance marker movement — approach.** The 10s poll (already existing, unchanged) can make the ambulance's position jump between two real-world points that are far apart, which reads as broken/glitchy on a map. A `useSmoothCoordinate()` hook eases the *displayed* marker position from its previous spot to each newly-polled one over 1.5s (comfortably inside the 10s poll window, so each glide finishes well before the next update lands) — implemented with a plain `Animated.Value` used purely as a timing/easing driver: `.addListener()` reads its 0→1 progress on each frame and linearly interpolates `{latitude, longitude}` into React state, which is what actually gets passed to `<Marker coordinate={...}>`. Deliberately **not** using react-native-maps' own `AnimatedRegion`/`Marker.animateMarkerToCoordinate` imperative APIs — this project has `newArchEnabled: true` (`app.json`), and those native-marker-driven animation paths have a history of inconsistent behavior across react-native-maps versions under React Native's New Architecture, whereas plain `Animated.Value` driving JS-side state (`useNativeDriver: false`, since the "native prop" being driven is arbitrary lat/lng math, not a style property) has no such dependency. The very first coordinate ever received for a given marker is shown immediately rather than animated in from nowhere (nothing sensible to glide from yet); an unchanged position between polls is a no-op (no restarted animation, no wasted work). This hook now lives in `mobile-frontend/hooks/use-smooth-coordinate.ts` (extracted in the EMT-side pass below, since both screens need it) — `emergency-active.tsx` no longer has its own inline copy.

  **EMT-side map + location sending (SC-15) — done.** `mobile-frontend/app/(ambulance)/active-response.tsx` now has the other half of this feature: while an EMT is on this screen for an accepted incident, a `useEffect` (scoped to `[incidentId]`, single `setInterval`, everything guarded by a `cancelled` flag set in the cleanup function — same discipline as every other polling loop in this codebase) calls `Location.requestForegroundPermissionsAsync()` + `Location.getCurrentPositionAsync({})` (the exact pattern already established in `patient-dashboard.tsx`'s SOS trigger — no new expo-location usage pattern introduced) every 12s (task spec: 10-15s), updates the EMT's own marker from that device GPS reading directly, and `PATCH`es it to `/incidents/{id}/update_location/`. The interval is cleared on unmount (nav away, e.g. tapping "Add Notes" or the back arrow) same as any other screen's polling cleanup, and also stops itself early the moment the incident goes `completed`/`cancelled`: rather than running a *second* polling loop just to watch incident status, that check reuses the status field already present in every `update_location` response (`IncidentAmbulanceActiveSerializer` includes `status`) — free, no extra request. On a terminal status it clears the interval, alerts the EMT (covers the "patient cancelled while I was still en route" case, which the EMT's own status buttons can't otherwise surface), and navigates back to the dashboard.

  The map itself: patient marker from `incident.latitude`/`longitude` (fetched once via the existing `medical_detail` call — unchanged), EMT's own marker from the device GPS reading directly (**not** read back from the server's `ambulance_lat`/`lng` — the task was explicit that the device is the source of truth for the EMT's own position, and round-tripping it through the server would just add latency for no benefit). The real route polyline from `GET /incidents/{id}/route/` is decoded client-side via a small hand-written Google-polyline decoder (`mobile-frontend/utils/decode-polyline.ts` — the standard precision-5 algorithm; no new dependency needed for this, and reused as-is by the patient-side screen too — see below) and rendered instead of a straight line. When the route call is unavailable or fails, **no line is drawn at all** (not even a straight-line fallback) — both markers still render — per the explicit spec ("the map should still show both markers even without a route line"). Distance/ETA are shown in the existing address-row strip beneath the map, replacing "📍 Patient location shared" with e.g. "🚗 2.3 km away • ETA 6 min" whenever a route is available.

  **Route-call throttling — reasoning.** `GET /incidents/{id}/route/` cost real Google Routes API quota per call (see the pricing-tier note above), so it is deliberately *not* called on every 12s location tick — that would be ~5x more calls than useful, since a route recomputed after the ambulance moved 20m isn't meaningfully different from the last one. Instead `maybeFetchRoute()` combines two independent gates: a **distance gate** (only recompute once the EMT has moved ≥150m since the last route call's origin) combined with a **30s floor** (never call more often than that even if moving fast — e.g. on a highway, 150m can pass in a few seconds), and a **60s ceiling** that forces a recompute regardless of movement or the 30s floor. The ceiling isn't about the route actually changing while stationary — this project's Basic-tier Routes API call doesn't factor live traffic, so a genuinely stationary position's route/ETA wouldn't change — it's a resilience/retry mechanism: if the last call failed (network hiccup, transient 503 from the backend's own Google-failure handling), this guarantees another attempt within a bounded time instead of only retrying whenever the EMT happens to move 150m. Net effect at typical urban ambulance speed: a route call roughly every 30-60s rather than every 12s, without ever leaving the ETA more than a minute stale. The patient-side screen reuses this exact same reasoning and these same constants (150m/30s/60s) — see "Real route polyline (patient side) — done" above.

## Key architectural decisions already made (don't relitigate without discussion)

1. **AI calls are backend-only.** The Django `chatbot` app calls Anthropic's API server-side. The API key lives only in the backend's environment variables, never in either frontend.
2. **Chatbot consent is separate from data-sharing consent.** A patient can consent to sharing data with hospitals/ambulances without consenting to the AI chatbot using their profile as context, and vice versa.
3. **Chatbot responses are structured JSON**, not freeform text, so the frontend can reliably show a "consult a professional" banner without relying on string-matching the AI's wording.
4. **The chatbot does not autonomously trigger SOS or suggest emergency dispatch.** It can flag that a response touches on something serious (`needs_referral`), but never decides to call an ambulance — that stays a deliberate, manual action by the patient (same press-and-hold safety gesture as the main SOS button).
5. **One web app, not three.** Hospital Admin, Ambulance Admin, and MERA super-admin all log into the same web app at the same URL. The UI shown after login depends on the logged-in user's `role` — this is not three separate deployed applications.
6. **Secrets never go in Git.** `.env` files are gitignored in every project folder. Real secrets are shared between teammates privately (not via GitHub, Slack, or Discord in plaintext).

## Prototype safety bypasses — MUST be reinstated before any real launch

Running the Django test suite (`python manage.py test`) surfaced three places where real safety/verification logic has been deliberately disabled for prototype/demo purposes. These are not bugs — they were intentional shortcuts — but they mean the current prototype is **not safe to use with real patient data or real institutions.** Anyone touching auth, SOS, or medical profile verification should know these exist:

1. **Institutional account approval gate is bypassed.** `accounts/views.py`, `LoginView` — the check that blocks `pending`/`rejected` hospital and ambulance accounts from logging in is commented out (`# PROTOTYPE: approval gate bypassed; reinstate for production`). Right now, any institutional account can log in regardless of MERA approval status. (This is specifically about the pending/rejected *institutional-status* messaging. A separate, general `is_active` check exists in the same view and is *not* bypassed — see "Login now actually checks `is_active`" under the `accounts` app section above.)

2. **Patient SOS verification check is hardcoded to always pass.** `emergencies/services.py`, `_patient_is_verified()` — this function unconditionally `return True`s instead of actually checking the patient's verification status. Any patient, verified or not, can currently trigger a real SOS.

3. **Medical profile auto-verifies on submission instead of requiring hospital review.** `medical_profiles/models.py`, `submit_by_patient()` — sets `verification_status = VERIFIED` immediately instead of `PENDING` (comment: "Auto-verified for prototype — skipping hospital verification flow"). The hospital verification queue (SC-12/SC-12b) currently has nothing real to review.

**Before any real-world use, all three of these need to be re-enabled and tested.** Until then, treat every patient/institutional account in this system as unverified in practice, regardless of what their `verification_status` field says.

Verified with real headless-Chromium (CDP) automation, not just code review: simulated a tab going hidden for 20s (confirmed zero requests fired, vs. the pre-fix behavior of the interval free-running/getting throttled unpredictably), then simulated it becoming visible again and confirmed a GET fired within ~60ms plus a correctly-spaced next poll ~15s later. **If `VerificationQueue.jsx` or either `Dashboard.jsx` (see the "Lower priority" staleness note below) get polling added, apply this same hidden/visible pattern rather than a bare `setInterval` — it's a small addition (one `useEffect`-scoped event listener) and avoids reintroducing the same background-tab staleness bug there.**

   **Debugging gotcha worth remembering:** don't count raw `Network.requestWillBeSent` events (or entries in the browser's Network tab) as "number of API calls made." Every cross-origin call from this app (frontend on `:5173`, backend on `:8000`) that carries the `Authorization` header — i.e. basically every `apiCall()` — is a CORS "non-simple" request, so the browser fires an `OPTIONS` preflight immediately before the real request. That preflight is a separate network-level entry for the *same* URL, and the browser also skips it on subsequent identical calls once the preflight result is cached (`Access-Control-Max-Age`), so counts can look inconsistent call to call. A prior investigation session miscounted this way and concluded `IncomingAmbulances.jsx` was firing "4 duplicate requests" on mount; a rigorous re-test with console-level instrumentation (counting actual `apiCall()`/`fetch()` invocations, not network-level entries, and filtering by HTTP method) confirmed the real number was the expected React-StrictMode-doubled 2 in dev (1 in production) — there was no extra application bug. If a network-request count ever looks off by a clean multiple of 2, check for preflights before assuming duplicate fetch logic.
5. **Google/Apple sign-in on mobile** — currently broken/not working. Needs both the frontend OAuth flow and backend social-auth token verification.
6. **Real maps during an active incident** — patient and EMT views need an actual maps integration (e.g. Google Maps) showing live location, not a placeholder. **Done, both backend and both frontend sides** (see "Live location tracking + routing" under the `emergencies` app section above for the full write-up): `ambulance_lat`/`ambulance_lng` on `Incident`, `PATCH .../update_location/`, and `GET .../route/` (server-side Google Routes API call) all exist and are tested. `emergency-active.tsx` (patient) plots the patient's real location, the ambulance's live (polled, smoothed) location, and the real Google-computed route polyline. `active-response.tsx` (EMT, SC-15) sends the EMT's own device GPS to the backend every ~12s, shows it directly on a map alongside the patient marker, and renders the same real route/ETA. Both sides throttle the route call identically (~every 30-60s, distance-or-staleness gated, to control Google API cost — see the route-throttling reasoning note in that section) and degrade identically (route unavailable/failed → no line, both markers still render, no crash).
7. **Reloading/restarting the app mid-emergency lost the user's place** — real safety gap, not just UX: a patient with an active SOS, or an EMT with an assigned response, who force-reloaded or restarted the app landed back on the normal dashboard/login instead of back in their in-progress emergency. **Done** — see "Session-restore on app launch (SC-01)" under the `emergencies` app section above: `GET /incidents/my_active/` (new, tested) plus a shared `routeAfterAuth()` helper used by both app-launch session-restore (`(auth)/index.tsx`, previously had no auth check of any kind — a bigger pre-existing gap than the task assumed) and manual login (`login.tsx`). Also surfaced, as a side effect of testing this: `react-native-maps` doesn't support the web platform at all and currently breaks the entire app's web build — see that same section for details; unrelated to this fix, not addressed, worth knowing if web support for this app ever comes up.

   **Manual fallback for in-progress incidents — added in a follow-up session, closing a gap this item's own fix left open.** SC-01's `routeAfterAuth()` redirect was, until this fix, the *only* way to ever reach `emergency-active.tsx`/`active-response.tsx` for an incident that already existed — `emergency-history.tsx` (patient) and `ambulance-history.tsx` (EMT/ambulance) both already listed in-progress incidents correctly (right status label, live "Active" counts) but neither screen's rows were tappable into anything; they were purely read-only. If the auto-redirect didn't fire for any reason, there was no other path in the UI to reach a live incident at all.

   This stopped being theoretical: a real dispatched incident (`on_the_way`) got permanently stuck on the deployed backend during testing. Root cause, found by direct DB/audit-log investigation: the ambulance account that had accepted and progressed it got deactivated mid-response (most likely a side effect of testing the MERA-admin deactivate feature against the same shared test account) — `LoginView` correctly refuses `is_active=False` accounts (see "Login now actually checks `is_active`" above), so that account could no longer log in, `my_active`'s redirect could never fire for it again, and the patient couldn't cancel either (at the time, `cancel_incident()` only allowed `PENDING_CONFIRMATION`/`ACTIVE` — cancellation was blocked the moment an ambulance was dispatched; **this exact rule was loosened in a later follow-up, see "Cancellation window widened" further below**). With no manual fallback in the UI, that incident had no way to ever be reached or resolved by anyone. `my_active`'s own status filter and its "more than one non-terminal incident is ambiguous, don't guess" guard (see SC-01 above) were both individually correct — the actual failure mode was the *combination* of an account lockout with zero alternate navigation path, a combination neither of those two pieces was ever meant to handle alone.

   Fix, on both sides, same shape: a history/log row now branches on whether its incident's status is terminal (`completed`/`cancelled`) or not.
   - **Non-terminal rows are now tappable straight into the live screen** — `emergency-history.tsx` navigates to `emergency-active.tsx`, `ambulance-history.tsx` navigates to `active-response.tsx`, both passing `{ incidentId: <that row's id> }` via `router.push`, the same param shape `patient-dashboard.tsx`/`dashboard.tsx` already use right after triggering/accepting a fresh incident. This, plus the SC-01 auto-redirect, are now the two paths into these screens — previously there was only the one.
   - **Terminal rows keep (patient) or gain (ambulance) expand-in-place behavior** rather than becoming permanently dead once resolved. The patient side already had this (`expanded` state, `numberOfLines` truncation, a "Tap to expand/collapse" hint); `ambulance-history.tsx` didn't have any expand affordance before this fix (every card was a static, always-fully-expanded `<View>`) — added to match, for the same reason the on-screen hint text now differs by resolution state (`"Tap to view live tracking →"` vs. `"Tap to expand ▼"`/`"Tap to collapse ▲"`) rather than silently changing what tapping a card does with no visual cue.

   **`active-response.tsx` had its own "only ever reached one way" assumption, independent of the history-screen gap above, and it would have undermined this fix if left as-is.** Its local `status` tracker (used to highlight which of the On the Way / Arrived buttons has already been pressed) was initialized to `'waiting'` unconditionally and only ever updated by this screen's own button handlers — it was never synced from the incident's actual fetched status. That's a correct assumption *only* if the screen is always entered immediately after accepting a fresh alert (status `dispatched`, nothing pressed yet) and never left before completion — true for the original flow, false the moment this fix makes the screen reachable for an incident that's already `on_the_way`/`arrived_on_scene`. Fixed by syncing local `status` from the fetched incident's real status in `fetchIncident()`. The screen also gained the same defensive "redirect to dashboard if the incident turns out to already be `completed`/`cancelled`" check `emergency-active.tsx` already had — belt-and-suspenders, since the history screen's own resolved/non-terminal branch should prevent this case from being reached that way, but the incident's status can also change server-side (completed by someone else, timing) between the list being fetched and the tap landing.

   **One more fix, adjacent but directly relevant to this exact stuck-incident scenario:** `emergency-active.tsx`'s cancel handler used to call the try/catch around the cancel API request but then unconditionally `router.replace()` to the dashboard *outside* the try/catch — meaning a failed cancel (e.g. exactly this case: status already past `ACTIVE`, backend correctly rejects it) silently navigated the patient away as if cancellation had succeeded, with the incident still genuinely live behind them. Left as-is, this would have actively undermined the whole point of making the screen reachable again: a patient reaching a stuck `on_the_way` incident through the new tap-through, tapping the always-visible "Cancel Emergency" button, and being misled into thinking it worked. Fixed to only navigate away on a successful cancel, and to show `Alert.alert('Could Not Cancel', ...)` on failure instead of silently leaving.

   **Cancellation window widened — product decision, added in a further follow-up.** Cancellation used to be blocked the instant an ambulance was dispatched (`cancellable = {PENDING_CONFIRMATION, ACTIVE}` in `cancel_incident()`, `emergencies/services.py`) — this was the actual rule in effect during the stuck-incident scenario documented above, and part of why that patient had no recourse. Product decision: a patient can now cancel through and including `ON_THE_WAY`, but not once `ARRIVED_ON_SCENE` or later — reasoning being that before the crew is physically on scene, cancelling still saves resources on a false alarm, but once they're there, only the crew on scene can assess and resolve the situation, not the patient unilaterally. `cancellable` is now `{PENDING_CONFIRMATION, ACTIVE, DISPATCHED, ON_THE_WAY}`. Covered by `emergencies/tests.py::SOSCancelTest` (`test_cancel_dispatched_incident`, `test_cancel_on_the_way_incident`, `test_cannot_cancel_arrived_on_scene_incident` — the existing `test_cannot_cancel_completed_incident` already covered the terminal-status side).

   **Keeping the ambulance side correctly informed, now that cancellation can happen post-dispatch — investigated before implementing, not assumed.** Before this change, cancellation and "an ambulance is assigned" were mutually exclusive states (dispatch requires `ACTIVE`→`DISPATCHED`, and cancellation was only ever legal pre-dispatch), so an assigned ambulance/EMT learning that "their" patient cancelled was never a real code path — it simply couldn't happen. It's a real path now, so this was checked point by point rather than assumed fine:
   - **`active-response.tsx` already handles this correctly, and already anticipated it.** Its 12s `update_location` PATCH loop reads `status` back from every response (`IncidentAmbulanceActiveSerializer` includes it) and already treats `completed`/`cancelled` as "stop the interval, alert the EMT, navigate to dashboard" — this was built during the SC-15 live-location work specifically to cover "patient cancelled while I was still en route" (see that section above), a case that, before today, could never actually trigger. It does now, and the existing handling is correct as-is — no changes needed there.
   - **`_get_assigned_incident()`** (the ownership lookup shared by `update_location`/`update_status`/`select_hospital`/`treatment_notes`) only checks `ambulance_service == effective_ambulance_service`, not `medical_profile_access_granted` or incident status — so none of those endpoints start 404ing for the assigned ambulance just because the incident got cancelled. The EMT can still submit treatment notes, etc. for a cancelled incident's record if needed; nothing about cancellation locks them out of the incident itself.
   - **`medical_detail`** (`IsAcceptingAmbulance`) *does* check `medical_profile_access_granted`, which `Incident.update_status()` already correctly flips to `False` on cancellation (NFR-04 — the same flip completion already triggered; cancellation was just never reachable post-grant before now). This only matters if something calls `medical_detail` again after cancellation — `active-response.tsx` only calls it once, on initial mount, so this doesn't disrupt an open session; it just correctly closes off access to the medical profile going forward, same as completion already does.
   - **`my_responses`/`ambulance-history.tsx`** has no status filter — it already lists a cancelled incident correctly, right alongside completed/other in-progress ones, with no separate handling needed (this predates today's change, from the manual-fallback fix above).
   - **`my_active`** correctly stops returning a cancelled incident (it's in the terminal-status exclude list), so a later relaunch/session-restore won't route the EMT back into a dead incident.
   - **`active_alerts`** (the pre-accept broadcast queue) is unaffected either way — it only ever lists unassigned `ACTIVE` incidents, and this change only concerns incidents that already have an ambulance assigned.
   - Added a `_notify(...)` stub call in `cancel_incident()` (guarded on `incident.ambulance_service_id` being set, so pre-dispatch cancellations — which have no ambulance to notify — don't call it) — matching the same logger-stub convention every other state-transition point in `services.py` already follows (`accept_incident` notifies the patient, `select_destination_hospital` notifies the hospital). This is a log-line stub, not a real push notification (this project has none — see the module docstring), and isn't what actually keeps the EMT's live screen informed; the `update_location` response is.
   - **One pre-existing edge case, not a regression from this change:** if the EMT never grants location permission, `active-response.tsx`'s `sendLocationTick()` returns before calling `update_location` at all, so that particular EMT wouldn't learn of a cancellation from this loop specifically. Not addressed here — the same permission denial already breaks the screen's core live-location/map functionality regardless of cancellation, and `my_active` still correctly stops re-routing them to a cancelled incident on their next app launch either way.

   **Mobile: `emergency-active.tsx`'s Cancel button now hides once cancellation is no longer possible, instead of staying visible only to fail.** Previously the button was unconditional — always rendered regardless of status — relying entirely on the backend rejecting the request (with the "Could Not Cancel" alert added in the fix above) once past `ACTIVE`. Matching this codebase's established "prevent the action, don't just error after the fact" pattern (see `register.tsx`'s consent checkbox), the button is now gated on a `canCancel` check that mirrors the backend's cancellable set exactly (`pending_confirmation`/`active`/`dispatched`/`on_the_way`; defaults to cancellable while `incident` is still `null`/loading). Once `arrived_on_scene` or later, the button is replaced with a plain informational notice ("The crew is on scene — cancellation is no longer available...") instead of disappearing with no explanation. The backend remains the real enforcement point regardless — this is UX, not the security boundary.

## What NOT to suggest

- Don't suggest calling the Anthropic API directly from either frontend.
- Don't suggest merging Hospital Admin, Ambulance Admin, and MERA super-admin into fewer/more roles without flagging it as a discussion point first — the current five-role split reflects real product requirements from project mentor feedback.
- Don't suggest self-registration flows for EMTs, Hospital Admins, or Ambulance Admins — these are intentionally admin-created only.
- Don't suggest storing secrets in code, committing `.env` files, or committing `venv`/`node_modules` folders.
- Don't suggest AI-driven autonomous emergency dispatch or SOS triggering.
- `hospital`/`hospital_admin` and `ambulance_service`/`ambulance_admin` ARE now treated as interchangeable in permission/role checks via `HOSPITAL_ROLES`/`AMBULANCE_ROLES` (see "Role naming" section above). If you find a check that compares against a single literal role string instead of these sets, flag it — that's a spot the migration missed, not the intended behavior.
- Don't build EMT self-registration flows on mobile — EMT accounts are created exclusively by their ambulance_admin.
